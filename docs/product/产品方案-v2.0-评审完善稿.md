# 肿瘤个人病案与病情轨迹系统 · 产品方案 v2.0（流程验证修订稿）

> 日期：2026-08-29  
> 定位：供产品、设计、研发、测试、合规共同对齐的阶段性基线方案  
> 输入：原 v1.2、专业评审、两位胰腺癌患者 62 份真实材料及本轮产品决策  
> 说明：本产品是患者/家属管理个人健康资料的 PHR，不是医院 EMR，不提供诊断或治疗建议。
> 首版载体：桌面 Web 端。

## 0. 执行摘要

### 0.1 当前阶段的核心判断

产品机会成立，但第一阶段不验证“医疗级解析是否已经成熟”，而是验证最基本的产品闭环：

**用户只上传资料 → 系统自动整理 → 用户看到结果 → 能快速找到原件 → 下次愿意继续上传。**

第一阶段的优先级固定为：

1. 流程跑通优先于功能齐全；
2. 用户零负担优先于逐项纠错；
3. 指标覆盖尽量广，准确率先建立真实基线；
4. 原件永远可见，识别失败不阻断归档；
5. 当前界面保持简单，底层数据保留后续演进能力。

### 0.2 一句话定位

**面向肿瘤患者家庭的自动病案整理工具：上传图片或 PDF 后，系统自动归档、提取和检索，帮助用户快速找到资料与原始报告。**

### 0.3 第一阶段允许什么、不允许什么

允许：

- 部分文档分类、日期、机构或指标识别不准确；
- 部分指标只能保留原文，暂时不能形成趋势；
- 不同医院、版式和指标的识别效果存在差异；
- 先记录准确率基线，再逐轮改善。

不允许：

- 因识别失败而丢失原件；
- 为提高准确率强迫用户逐项录入或校对；
- 把低可信数据包装成诊断、疗效或风险结论；
- 不同账号之间出现资料串读；
- 当前简化实现破坏原始数据，导致未来无法重新解析。

### 0.4 第一阶段成功标准

- 首次用户无需培训即可完成一批资料上传；
- 上传成功的原件可以稳定保存、打开和删除；
- 用户在 5 分钟内看到第一批自动整理结果；
- 用户能在 30 秒内找到指定资料并打开原件；
- 用户无需补录大量信息，也愿意在下次检查后继续上传；
- 系统获得覆盖广泛、口径真实的解析准确率基线，为后续优化提供依据。

## 1. 产品战略与边界

### 1.1 目标用户

主用户是实际整理资料、陪同就诊的家属照护者；次用户是能自主使用电脑浏览器的患者。

第一阶段按“一个账号、一个患者”设计。用户只需填写患者姓名或昵称，用于避免上传错人；不要求录入完整人口学资料、诊断、治疗方案或病史。

### 1.2 第一阶段用户任务

| 场景 | 用户操作 | 系统责任 |
|---|---|---|
| 首次建档 | 填写姓名或昵称 | 创建单患者病案空间 |
| 批量归档 | 选择相册图片或 PDF 并上传 | 保存原件、自动分类、识别日期和内容 |
| 查看结果 | 打开整理完成页面 | 展示病案事件、识别字段及来源原件 |
| 查找资料 | 搜索关键词或按时间浏览 | 返回相关文档并可直接打开原件 |
| 后续补档 | 再次上传新资料 | 自动追加，不要求重复录入 |
| 发现错误 | 可选点击“识别不准确” | 记录反馈，不阻断使用，不要求手工修正 |

### 1.3 产品原则

1. **上传即用**：除患者姓名或昵称外，不设置必填医疗字段。
2. **原件优先**：结构化结果是索引和辅助，原始报告始终保留。
3. **自动降级**：识别不完整时进入“仅原件”，不要求用户完成系统工作。
4. **宽覆盖、真实报告**：尽量识别更多指标，但不宣称所有指标具有同等准确率。
5. **少做判断**：展示报告事实，不命名病情、不推断疗效、不建议处置。
6. **非破坏性演进**：原文、原图、OCR、解析结果和版本分别保存，未来可以重新解析。
7. **简单界面、可扩展底座**：第一阶段不展示复杂功能，但稳定保留患者、文档、事件、字段和来源关系。
8. **最低安全底线不延后**：账号隔离、原件保护、授权同意和删除能力从第一阶段开始具备。

### 1.4 明确不做

以下不是后续路线图能力，原则上不纳入本产品：

- 诊断、疗效判定、治疗或用药建议、生存期预测、急症分诊；
- 自动 RECIST、影像阅片、DICOM 诊断分析；
- 自动生成“进展、恶化、复发、危险”等医学判断；
- 用患者数据训练通用模型，或向第三方出售医疗数据；
- 医患聊天、线上问诊、医生工作站和患者社区。

## 2. 第一阶段信息架构与核心流程

### 2.1 页面结构

第一阶段采用桌面 Web 端，只保留三个核心页面：

1. **首页/上传**：上传入口、最近资料、处理进度；
2. **病案**：按时间浏览、关键词搜索、简单筛选；
3. **详情**：查看原件、OCR 文本和自动识别字段。

“趋势”作为实验入口放在指标详情中，不占独立一级导航。“我的”只保留账号、隐私、反馈和删除等必要设置。

### 2.2 首次使用闭环

创建患者 → 批量选择图片/PDF → 上传原件 → 自动处理 → 展示整理结果 → 搜索或打开原件

用户完成上传后即可切换页面或关闭标签页。系统异步处理完成后展示站内任务提醒；用户主动授权且浏览器支持时，可发送不包含医学内容的浏览器通知。

### 2.3 用户可见状态

每份文件只展示四种容易理解的状态：

- **处理中**：文件已保存，系统正在识别；
- **已整理**：已生成可查看的分类或字段结果；
- **仅原件**：暂未可靠识别，但可以搜索 OCR 文本和查看原件；
- **处理失败**：原件仍然保存，用户可以一键重试。

内部可以保存更细的置信度和错误类型，但第一阶段不要求用户理解复杂评分，也不产生待办式校对任务。

### 2.4 病案组织

病案默认按检测或文档日期排序；日期无法识别时按上传时间排序并标注“日期未识别”。

第一阶段采用保守合并：

- 完全相同的文件哈希可以判为重复上传；
- 相似图片或相似指标只标记为“可能重复”，不自动删除或覆盖；
- 所有原件均保留，未来可以重新合并为临床事件。

### 2.5 搜索

搜索从第一阶段覆盖：

- 原始 OCR 文本；
- 自动识别的文档类型、机构和日期；
- 指标原始名称、标准名称和值；
- 文件名和用户上传时间。

搜索结果必须可以直接打开对应原件。即使结构化识别失败，原始 OCR 文本仍可提供检索价值。

### 2.6 详情与证据

详情页采用“原件优先、结果辅助”的结构：

- 默认展示原件缩略图和文档基本信息；
- 自动识别字段显示原始名称、结果、单位、参考范围和日期；
- 点击字段可以定位到对应页面或原文区域；
- 明确标注“自动识别结果可能不准确，请以原始报告为准”；
- 用户可以选择一键反馈识别不准确，但不要求填写正确值。

### 2.7 实验性趋势

为了验证未来价值，第一阶段可以提供少量、弱承诺的实验性趋势：

- 只连接标准名称一致、数值可解析、单位相同且日期明确的数据；
- 单位不同、方法不明或结果为定性描述时不连线；
- 所有点均可打开原件；
- 页面固定标注“实验性整理结果，不用于诊断或疗效判断”；
- 趋势使用情况和误读情况只用于决定是否继续完善，不作为第一阶段主流程成败的唯一标准。

## 3. 指标覆盖与解析策略

### 3.1 宽覆盖策略

第一阶段保留至少 125 项检验指标字典，并允许持续增加常见别名。覆盖目标是“尽量识别并可搜索”，不是“所有指标立即达到医疗级准确率”。

每个指标尽量抽取：

- 原始指标名称；
- 标准名称或候选标准名称；
- 原始结果；
- 原始单位；
- 参考范围或定性结果；
- 检查日期；
- 来源文档、页码和原文位置。

支持的结果形式包括：

- 普通数值；
- 大于、小于等带比较符号的数值；
- 未检出、阳性、阴性、溶血、拒收、未报告等状态；
- 加号等级和其他半定量结果。

### 3.2 能力分级仅用于内部

为方便后续优化，后台将指标分为：

- **稳定项**：已有较多样本，字段识别相对稳定；
- **探索项**：能够识别但准确率和版式覆盖尚未充分验证；
- **仅检索项**：保留 OCR 原文和候选结果，暂不进入趋势。

该分级不要求用户选择或确认，也不增加用户操作。前台只展示原件、自动结果和必要说明。

### 3.3 简化解析流水线

1. 文件安全检查、格式识别、旋转和清晰度检测；
2. 原件保存并生成不可变文件标识；
3. OCR 或 PDF 文本层提取；
4. 文档类型、日期和机构候选识别；
5. 指标名称、结果、单位和参考范围抽取；
6. 指标字典候选映射；
7. 基础一致性校验；
8. 保存解析版本、来源位置和处理状态；
9. 生成病案列表、搜索索引和可选实验趋势。

第一阶段不建设复杂的用户复核工作台、人工审核队列和历史字典迁移界面，但必须保存原始数据、字典版本和解析版本，确保后续可以补建。

### 3.4 错误处理

- 低置信结果可以展示为自动识别结果，但不得生成医学判断；
- 无法确认名称、数值或单位关联时，保留原文，不进入趋势；
- 极端值不删除，只保留并指向原件；
- 用户反馈只记录错误样本，不要求用户完成正确答案；
- 新模型或新规则上线后，可以基于原件重新解析并生成新版本；
- 旧结果保留审计，不覆盖原始 OCR 和原始文件。

## 4. 数据模型与后续演进

### 4.1 第一阶段核心模型

Account → Patient → Document → DocumentPage  
Patient → ClinicalEvent → ExtractedField / LabResult  
Document / DocumentPage → SourceEvidence  
解析任务 → ProcessingRun → ParsingVersion

关键要求：

- 原始文件不可变，解析结果可版本化；
- 每个字段都能回到来源文档和页面；
- 日期支持日、月、年和未知精度；
- 原始值与标准化候选值分别保存；
- 文件、事件和字段均使用稳定标识，避免未来扩展时迁移主键；
- 任何自动合并都必须可撤销。

### 4.2 只预留、不提前建设的扩展点

第一阶段只确保核心标识和数据关系不封死后路，不建设复杂界面或完整工作流：

- Membership：未来多账号和家庭成员；
- ShareGrant：未来分享有效期、范围和撤销；
- ReviewTask：未来用户确认、专业复核和人工审核；
- AuditLog：未来完整修改、访问和导出审计；
- DerivedArtifact：未来速查卡、PDF 和其他派生材料；
- TreatmentRegimen、Diagnosis、StagingSnapshot：未来治疗、诊断和分期结构化；
- Pathology、GeneVariant、Lesion：未来病理、基因和病灶能力。

“预留”只指稳定数据标识、来源关系和扩展接口，不意味着第一阶段提前开发空功能。

### 4.3 后续能力路线图

| 阶段 | 目标 | 主要新增能力 |
|---|---|---|
| 阶段 1：流程验证 | 证明上传、整理、检索、回看原件能闭环 | 单患者、批量上传、宽指标抽取、搜索、详情、实验趋势 |
| 阶段 2：准确率与可信 | 提升自动结果可用性 | 高风险路由、用户一键确认、专业复核、字典审核、可比性规则、金标准评测 |
| 阶段 3：就诊使用 | 证明诊室和转院价值 | 就诊速查卡、诊断/分期/治疗事实、影像病理原文摘录、PDF、原件/结构化导出、回收站与恢复；离线查看本期暂缓 |
| 阶段 4：家庭协作 | 支持真实照护接力 | 多患者切换、家庭成员、可见范围、分享、撤销、生命周期归档、完整审计 |
| 阶段 5：领域深化 | 扩展复杂肿瘤资料组织 | 治疗周期、病理/基因结构化、经验证的病灶锚定和更多纵向能力 |

## 5. 第一阶段交付范围

### 5.1 必须交付

1. 单账号、单患者建档，患者仅需姓名或昵称；
2. 图片/PDF 批量上传、异步处理、失败重试和原件保存；
3. 文档类型、日期、机构自动候选识别；
4. 至少 125 项检验指标字典与宽覆盖抽取；
5. OCR 全文检索和结构化字段搜索；
6. 按时间组织的病案列表；
7. 原件、识别结果和来源位置查看；
8. 完全相同文件去重与相似文件提示；
9. 少量符合基础条件的实验趋势；
10. 可选的一键错误反馈；
11. 最小必要的同意、账号隔离、访问保护和删除能力；
12. 记录上传完成率、处理耗时、识别覆盖、搜索使用和再次上传等数据。

### 5.2 明确延后

- 逐字段手工录入和强制校对；
- 当前诊断、分期、治疗方案、影像和病理的自动摘要；
- 正式就诊速查卡、PDF、离线包和结构化导出；
- 多患者切换、家庭协作、复杂分享权限；
- 回收站、完整审计后台和专业复核工作台；
- 跨医院复杂可比性、单位换算和治疗背景叠加；
- 医学级准确率承诺和公众放量。

### 5.3 后续兼容验收

第一阶段完成时必须确认：

- 原件能够被新解析器重新处理；
- 解析版本可并存，可回退到旧结果；
- 字段都有稳定标识和来源；
- 新增指标不需要修改文档主模型；
- 未来增加多患者和家庭成员时不需要重建患者数据；
- 未来生成速查卡、PDF 和导出包时可以复用现有来源链。

## 6. 验收与指标体系

### 6.1 流程验收门槛

| 指标 | 第一阶段目标 |
|---|---|
| 无指导上传完成率 | 真实用户中 ≥80% 能独立完成首次批量上传 |
| 原件保存成功率 | 系统显示上传成功的文件 100% 可重新打开 |
| 首个结果时间 | 测试网络和约定批量规模下，上传结束后 5 分钟内看到第一批结果 |
| 失败可恢复率 | 处理失败文件均保留原件并可一键重试 |
| 30 秒找资料成功率 | 5 个指定查找任务中，用户正确完成 ≥4 个 |
| 强制医疗录入项 | 0 |
| 跨账号串读 | 0 |
| 再次使用意愿 | 多数试用用户愿意在下一次检查后继续上传 |

“再次使用意愿”同时记录访谈结论和真实后续上传，不只依赖问卷。

### 6.2 解析指标只建立基线

第一阶段报告但不作为流程上线硬门槛：

- 文档分类准确率；
- 日期和机构识别准确率；
- 指标名称、结果、单位和参考范围的精确率与召回率；
- 125 项字典中的实际命中覆盖；
- 按医院、文档类型、版式和指标分层的错误分布；
- 仅原件比例、趋势可用比例和用户错误反馈率。

评测必须同时保留成功子集和全量口径，不通过排除失败样本美化结果。

### 6.3 阶段决策

满足以下条件即可认为流程假设成立：

- 用户不依赖培训或大量补录即可完成上传；
- 原件、病案列表、搜索和详情形成完整闭环；
- 即使部分识别不准确，用户仍能依靠原件找到所需资料；
- 用户对继续上传有真实意愿。

出现以下任一情况应暂停扩功能，先修流程：

- 用户普遍无法完成上传；
- 原件丢失、无法打开或跨账号可见；
- 用户必须大量手工录入才能获得价值；
- 用户看完整理结果后仍找不到目标资料；
- 多数用户不愿再次使用。

## 7. 合规、隐私与安全底线

第一阶段虽是封闭验证，仍处理医疗健康敏感个人信息，以下能力不能延期：

- 明确处理目的、范围、保存期限和退出方式，取得必要同意；
- 若上传亲属资料，明确上传者的授权责任；
- 原件、缩略图、OCR、搜索索引和日志均按敏感数据保护；
- 账号和患者数据严格隔离；
- 外部 OCR 或模型服务在调用前完成处理角色、留存、删除和跨境评估；
- 不允许第三方将数据用于其通用模型训练；
- 用户可以停止使用并删除资料；
- 已授权用于测试的真实样本与产品数据分开管理。

在扩展公众使用、就诊速查卡或更强医学结构化能力前，完成个人信息保护影响评估、伦理路径判断和医疗器械属性预判。

## 8. 成本与运行护栏

第一阶段只需要验证真实成本结构，不提前设计复杂收费体系。

需要记录：

- 每页 OCR/模型调用成本；
- 首次批量上传峰值和平均处理时间；
- 原件、缩略图和搜索索引存储成本；
- 失败重试和重新解析成本；
- 每个活跃患者的月均新增页数。

封闭试用采用明确配额。超限时暂停新增解析，但仍允许查看和删除已有原件，不静默降低处理质量。

## 9. 研究与验证计划

### 阶段 A：流程原型

- 完成上传、处理状态、病案列表、搜索、详情和原件回看闭环；
- 用已有且授权范围明确的样本验证格式兼容和字段模型；
- 指标字典覆盖至少 125 项，不追求统一高准确率。

### 阶段 B：真实用户封闭试用

- 招募 8–10 名真实照护者；
- 每位用户上传一批自己的图片或 PDF；
- 不提供操作培训，仅观察是否能独立完成；
- 记录上传阻塞、处理等待、搜索失败和需要手工解释的环节；
- 访谈用户是否愿意在下次检查后继续使用。

### 阶段 C：决定下一步

- 流程成立：进入准确率与可信能力建设；
- 上传成立但整理价值弱：优先优化病案组织和搜索；
- 用户主要依赖原件：保留归档价值，谨慎投入复杂趋势；
- 用户不愿再次上传：停止扩功能，重新审视产品定位。

## 10. 已确认的产品决策

1. 第一阶段只验证系统流程能否跑通，不以医疗级准确率作为前置条件；
2. 用户以上传资料为主要操作，不要求大量录入、逐项确认或手工纠错；
3. 指标尽量宽覆盖，至少保留 125 项字典和扩展能力；
4. 识别失败时保留原件和搜索能力，不阻断归档；
5. 第一阶段界面和功能保持简单；
6. 已规划且符合产品边界的能力全部进入后续路线图；
7. 当前通过稳定标识、原始数据保留、版本化和来源链支持后续完善，不提前建设复杂空功能；
8. 诊断、疗效判断和治疗建议等明确不做项不因路线图扩展而改变。

## 11. 产品北极星与阶段目标

第一阶段北极星：

**首次上传后，用户能够在需要时重新打开产品，并在 30 秒内找到一份目标资料或原件。**

辅助指标：

- 完成首次上传的用户比例；
- 7 天内再次打开病案、搜索或查看原件的用户比例；
- 发生新检查后再次上传资料的用户比例；
- 每次查找目标资料的成功率和耗时。

后续进入就诊使用阶段后，再升级为：

**每月发生新就诊或检查后，用户在 7 天内完成归档，并至少一次在真实任务中使用病案、速查或趋势的患者比例。**

北极星必须围绕真实任务完成，不能用注册数、文件数或 OCR 次数替代。
