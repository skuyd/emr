## 0. 一页纸摘要

| 项 | 内容 |
|----|------|
| **一句话定位** | 面向肿瘤患者家属的病案归集与病情趋势管理工具——把散落在各家医院的检验检查单据，自动变成一条可对比、可追溯、可交给医生的病情时间轴。 |
| **目标用户** | 主用户：家属照护者（患者子女为主）；次用户：患者本人（长辈模式） |
| **核心价值** | ① 单据不再丢失、不再翻箱倒柜 ② 同一个指标跨时间的纵向对比，一眼看出趋势 |
| **首期形态** | 微信小程序（主）+ 轻量 Web 端（深度整理用） |
| **首期范围** | 125 个检验指标的全自动解析（Tier1 核心 70 优先）+ 单据归集 + 时间轴 + 纵向对比（V1） |
| **支持格式** | 图片（手机拍照/扫描件）、PDF（扫描型/文本型） |
| **明确不做** | 诊疗建议、用药推荐、生存期预测、完整 RECIST 自动判定、主动预警推送、**单张报告的医学解读**（医院 LIS 已自带，非差异化） |
| **差异化** | **跨时间的纵向趋势 + 跨医院的数据归集**——医院系统看不到患者在其他医院的完整数据 |
| **最大风险** | ① 版面分栏失败导致指标-数值错位 ② 参考范围解析错误导致异常判定错误。策略：接受一定错误率，靠「原文一键回溯」让用户随时可验证 |

## 1. 产品定位与边界

### 1.1 定位

C 端自用的**个人病案助手（PHR）**，不是医院信息系统，不承担任何诊疗职能。

关键分界：**本系统只回答"你的数据是什么、怎么变的"，不回答"这意味着什么、你该怎么办"。**

### 1.2 用户画像

**主画像：家属照护者（张女士，38 岁，父亲肺癌 IIIB 期）**

| 维度 | 描述 |
|------|------|
| 场景 | 父亲确诊 8 个月，经历手术 + 4 周期化疗，目前在免疫维持治疗。每周陪父亲去一次医院，手上有 80+ 张各类单据 |
| 痛点 | ① 医生问"上次 CEA 多少"答不上来 ② 换专家时要重新整理一遍病史 ③ 纸质单据发黄丢失 ④ 手机相册里单据和生活照混在一起 |
| 能力 | 熟练使用微信，愿意花时间整理，但不懂医学术语（不知道 ANC 是什么） |
| 期望 | "我不需要懂医，我只想在医生问的时候能马上答出来" |

**次画像：患者本人（张先生，65 岁）**

只需要：拍照上传、看大字的结论、不迷路。对应 V4 的「长辈模式」。

### 1.3 价值主张

| 层级 | 主张 | 对应功能 |
|------|------|---------|
| 地基 | 所有单据一处收拢，永不丢失 | 批量导入、自动分类、检索 |
| 核心 | 同一指标跨时间对比，趋势一目了然 | 纵向多列对比、sparkline、异常分级 |
| 钩子 | 看医生时一页纸说清病情 | 一页纸病情摘要 PDF |
| 信任 | 数据错了能立刻发现 | 原文一键回溯、对照模式 |

> **说明**：原讨论中"异常预警"与"就诊准备"未被列为首期价值锚点。但"一页纸病情摘要"在数据已结构化的前提下生成成本极低（本质是已有数据的一种输出格式），故保留为 V2 标准模块；"异常预警"降级为 V4 的陈述式复查提醒，不做主动推送。

### 1.4 Non-goals（明确不做）

| 不做 | 原因 |
|------|------|
| 诊疗建议、用药推荐、生存期预测 | 触及二类医疗器械（SaMD）监管红线，C 端产品承担不起 |
| 主动推送式异常预警 | 加重患者焦虑；误报的伤害大于漏报的收益 |
| 完整 RECIST 自动疗效判定 | 需要专业靶病灶管理，投入产出比低；改为呈现报告原文结论 + 最大病灶大小趋势线 |
| 对接医院 HIS / 区域健康平台 | 门槛极高、周期长，C 端产品不具备条件；坚持"用户上传"单一数据入口 |
| 医生端 / 医患沟通 | 定位是患者自用工具，一旦引入医生角色，合规等级与复杂度量级上升 |
| 原始影像（DICOM）处理与阅片 | 只存不处理，不做影像分析 |

### 1.5.2 关键发现与方案修正

#### 发现 A：检验报告格式高度规整

海南省肿瘤医院的检验报告单采用统一表格结构：

```
序号 | 代号 | 项目名称 | 结果 | 单位 | 参考范围 | 测试方法 | 互认标识
  1  | *CEA | 癌胚抗原 | 2.29 | ng/mL | <4.5    | 化学发光法 | 海南省HR
```

异常标记用 ★ 前缀 + ↑/↓ 箭头。参考区间格式多样：`<25`、`<44`、`3.1--8.8`、`阴性`、`S/CO >1`。

**修正**：解析模板可按此结构设计，覆盖国内主流 LIS 输出格式。互认标识（如"海南省HR"）可作为元数据保留但不影响解析。

#### 发现 B：PDF 文本提取存在系统性 OCR 错误

从 YMHU1.pdf（文本型 PDF 的 pdfplumber 提取结果）观察到：

| 错误类型 | 示例 | 实际值 | 影响 |
|---------|------|-------|------|
| 数字被空格断开 | `131.7 0` | 131.70 | 数值截断 |
| 小数点后数字断开 | `10. 54` | 10.54 | 同上 |
| 字母 O 与数字 0 混淆 | `<O. 05` | <0.05 | 参考区间误判 |
| 字母 l 与数字 1 混淆 | `2026-0l-l1` | 2026-01-11 | 日期错误 |
| 异常箭头误识别为文字 | `668. 75个` | 668.75 ↑ | "个"实际是 ↑ 箭头 |
| 单位字符乱码 | `IU/rnL` | IU/mL | 单位匹配失败 |
| 检验者姓名乱码 | `王卡卞卞卜` | （人名） | 不影响指标抽取 |

**修正**：四层校验增加第 0 层——**数字格式预修复**（合并断开的小数段、O→0/l→1 置换、箭头符号归一化）。这一层在值域校验之前执行，成本极低但能拦截大量低级错误。

#### 发现 C：大量关键指标散落在病程记录的自由文本中

营养科会诊记录（2026-05-26）中直接写明：

> 血常规五分类 白细胞 10.38×10⁹/L、红细胞 2.56×10¹²/L、血红蛋白 90 g/L、血小板 62×10⁹/L；
> 电解质四项 钠 133.9 mmol/L；空腹血糖 葡萄糖 15.05 mmol/L；C反应蛋白 212.10 mg/L

内分泌会诊记录（2026-06-08）中：

> 糖化血红蛋白 8.8%、空腹C肽 1.04 ng/ml、尿微量白蛋白/肌酐比值 24.97 mg/g

这些值**不在任何一张化验单上**，而是医生在会诊时引用的关键值。

**修正**：L4 文书解析不能只做"治疗周期推断"，必须包含**自由文本中的指标值抽取**。这些值的置信度标注为"间接引用"（来自病程记录而非原始报告），与直接来自化验单的值区分展示。

#### 发现 D：CA19-9 趋势验证了基线漂移标记的价值

同一患者两次 CA19-9 检测：

| 日期 | CA19-9 (U/mL) | 参考上限 | 升幅 |
|------|--------------|---------|------|
| 2026-01-07 | 131.70 | <44 | — |
| 2026-07-07 | 329.93 | <44 | **+150%** |

CEA 同步从 2.29 → 6.34（+177%）。两者均在"超出参考区间"的基础上**持续大幅上升**——这正是"基线漂移 >30%"标记要捕捉的信号。

**修正**：胰腺癌场景下，CA19-9 和 CEA 应作为**默认置顶指标**（癌种自动推断后生效）。基线漂移阈值对肿瘤标志物可适当放宽至 >50%（因波动性更大）。

#### 发现 E：PET/CT 报告含 SUVmax 量化值

样本中 PET/CT 报告（2026-04-27）明确列出：

| 部位 | 大小 | SUVmax |
|------|------|--------|
| 胰头病灶 | 26mm×28mm | **12.4** |
| 左肺下叶结节 | 26mm×16mm | **10.1** |
| 肝囊肿 | 直径16mm | 1.2 |
| 左肾上腺增粗 | — | 1.9 |

SUVmax 是 PET/CT 最核心的疗效监测量化指标（代谢活性越高 = 越活跃）。

**修正**：影像关键字段表增加 **SUVmax**（仅 PET/CT 有）。SUVmax 可作为独立趋势线追踪（类似肿瘤标志物），比单纯测量尺寸更敏感地反映疗效变化。

#### 发现 F：影像报告自带中文疗效描述词

CT/PET-CT 报告的诊断意见中自然出现：

| 描述词 | 含义 | 对应 RECIST |
|--------|------|------------|
| "较前无明显变化"、"较前相仿" | 稳定 | SD |
| "较前稍改善"、"较前略减少" | 缩小/好转 | PR |
| "提示治疗后仍存较高活性" | 仍有活性 | PD/SD |
| "新发"、"增大" | 进展 | PD |

**修正**：不需要自己做 RECIST 计算。改为**抽取影像报告自带的疗效描述关键词**，作为"影像结论原文"的一部分展示。这比算法判定更权威（放射科医生的判断），且实现简单得多。

#### 发现 G：治疗史复杂度远超预期——需要多方案分组

该患者 22 个月内经历：

| 时间段 | 方案 | 类型 |
|--------|------|------|
| 2024-11 ~ 2025-01 | NALIRIFOX（奥沙利铂+亚叶酸钙+氟尿嘧啶+伊立替康脂质体） | 化疗 |
| 2025-02 ~ 2025-03 | AG 方案 + 替雷利珠单抗 | 化疗+免疫 |
| 2025-04 ~ 2025-06 | 卡培他滨 → 尼妥珠单抗+吉西他滨 | 维持→靶向 |
| 2025-07 ~ 2025-09 | NALIRIFOX + 尼妥珠单抗 | 化疗+靶向 |
| 2025-09 ~ 2025-11 | 卡培他滨维持 | 维持化疗 |
| 2025-11 ~ 2026-02 | NALIRIFOX + 尼妥珠单抗（多周期） | 化疗+靶向 |
| 2026-04 ~ 2026-05 | 紫杉醇白蛋白+吉西他滨 + 左肺转移灶放疗 | 化疗+放疗 |
| 期间穿插 | NK/T/AAT 细胞治疗 × 多次、海扶刀、替吉奥维持 | 细胞/物理/维持 |

**共 7 个不同方案组，每个方案组内各自编号周期**。不是简单的"C1/C2/C3..."线性序列。

**修正**：治疗周期模型从"单一序号"升级为**「方案分组 + 组内周期」**二维结构：
```
方案A: NALIRIFOX
  └── C1 (11-08) → C2 (11-25) → C3 (01-07)
方案B: AG + 替雷利珠单抗
  └── C1 (02-13) → C2 (03-25)
方案C: 紫杉醇白蛋白+吉西他滨
  └── C1 (05-04) → C2 (05-18)
```
界面展示时，方案组作为一级分组，组内周期作为二级节点。

#### 发现 H：体重/BMI 是胰腺癌的核心监测指标

患者身高 157cm、体重 36kg → BMI 14.6（严重营养不良，WHO 定义 <18.5 即为营养不良）。入院记录中明确诊断"营养不良"，营养科会诊评定 SGA C级（重度）、NRS 2002 4分。近 10 天体重下降 3kg（8%）。

**修正**：体重监测从 L5（V3）提前到 **V1 或至少 V2**。胰腺癌恶病质是首要死因之一，体重下降 >5%/月或 >10%/半年是明确的危险信号。体重数据来源：入院记录（每次住院必填）+ 患者自记录。

#### 发现 I：血糖管理需要专门的数据结构

该患者在治疗过程中新发糖尿病（糖化血红蛋白 8.8%），需 7 点血糖谱监测（空腹+三餐后 2h+睡前+凌晨）。这不是单次检验值，而是一个**日内多次的时序序列**。

**修正**：血糖数据单独建子表（非普通 LabItem），支持"一日多点"视图。V1 可暂不实现，但数据模型预留字段。

#### 发现 Q：CA19-9 完整进展曲线 —— 纵向对比价值的最强证据

对患者 A 的 27 张图片做 OCR 后，拼出了 CA19-9 的完整时间序列：

| 日期 | CA19-9 (U/mL) | CEA (ng/mL) | CA125 (U/mL) | 参考上限 |
|------|--------------|-------------|--------------|---------|
| 2026-01-07 | 131.70 | 2.29 | 10.54 | <44 / <4.5 / <35 |
| 2026-07-07 | **329.93** | 6.34 | 41.85 | ↑ 2.5 倍 |
| 2026-08-20 | **1327.66** | 9.99 | 83.36 | ↑ 10 倍 |

**7 个月内 CA19-9 从 131.7 升至 1327.66，涨幅超 10 倍**，且 CEA、CA125 同步上升。

**这张表就是整个产品存在的理由**：任何一张单独的报告都只显示"超出参考范围"，只有纵向对比才能揭示"持续加速上升"这个真正关键的临床信号。

**修正**：
1. 肿瘤标志物的**多指标联合趋势图**应作为核心视图（非单一指标曲线）
2. 基线漂移阈值对肿瘤标志物放宽至 >50%（波动性大，30% 会有过多噪声）
3. 上升速率（如"近 3 个月平均每月 +28%"）比绝对变化量更能反映临床意义，建议在趋势视图中展示

#### 发现 R：尿常规是"定性 + 半定量"混合指标 —— 异常判定需两套逻辑

样本中出现**尿液分析（干化学）**报告，其指标形态与血常规完全不同：

| 代号 | 项目 | 结果 | 参考范围 | 类型 |
|------|------|------|---------|------|
| PH | 酸碱度 | 7.5 | 4.5–8 | 数值 |
| SG | 尿比重 | 1.015 | 1.003–1.03 | 数值 |
| GLU | 尿葡萄糖 | **阳性（1+）5.6mmol/L** | 阴性(-) | **半定量** |
| PRO | 尿蛋白 | **阳性（1+）0.3g/L** | 阴性(-) | **半定量** |
| BIL | 尿胆红素 | **阳性（1+）17umol/L** | 阴性(-) | **半定量** |
| UBG | 尿胆原 | 弱阳性(±) | 弱阳性(±) | **定性** |
| BLD | 隐血 | 阴性(-) | 阴性(-) | **定性** |
| NIT | 亚硝酸盐 | 阴性(-) | 阴性(-) | **定性** |
| ASC | 维生素C | 阳性（1+）1.4mmol/L | 阴性(-) | **半定量** |
| — | 颜色 | 淡黄色 | 黄色 | **定性（非异常）** |

**问题**：原方案的异常判定基于"结果数值 vs 参考区间数值"的比较，对"尿蛋白 阳性(1+) vs 参考 阴性(-)"**完全不适用**。

**修正（重要）**：指标类型扩展为三类，异常判定配套两套逻辑：

| 类型 | 存储 | 异常判定逻辑 | 示例 |
|------|------|------------|------|
| **数值型** | value (float) + unit | 数值区间比较 | HGB 86 vs 115–150 |
| **定性型** | enum_value | **枚举匹配**：结果 ≠ 参考枚举值即异常 | 隐血 "阳性" vs 参考 "阴性" |
| **半定量型** | grade (1+/2+/3+/±) + value + unit | 枚举匹配为主，数值为辅 | 尿蛋白 "1+" + 0.3g/L vs "阴性" |

**数据模型补充**：`LabItem` 增加 `value_type`（numeric / qualitative / semi_quantitative）、`enum_value`、`grade` 字段。

> 这解释了为什么 Tier2 的尿常规在初版设计中被低估——它的处理逻辑与数值指标完全不同，不是"多几个字段"那么简单。

#### 发现 S：新的 OCR 错误模式 —— 小于号被识别为字母 K

同一份报告中观察到不一致的识别结果：

| OCR 输出 | 实际值 |
|---------|--------|
| `K4. 5` | `<4.5` |
| `K35` | `<35` |
| `<44` | `<44`（同一份报告中此处识别正确） |

**修正**：第 0 层数字格式预修复增加规则——`K` + 数字 组合（且位于参考范围列）→ 还原为 `<`。同时因为识别不稳定，**不能假设同一份报告内的错误模式一致**，每条参考范围都必须独立校验。

### 1.5.3 扫描件 vs 文本型 PDF 占比

| 类型 | 文件数 | 文本提取 | 处理方式 |
|------|-------|---------|---------|
| 文本型 PDF（HIS 导出） | Case ×2, YMHU1.pdf, CT ×2, 彩超, 基因检测 | ✅ 可直接抽取文本 | 跳过 OCR，准确率最高 |
| 扫描型 PDF（打印件扫描） | Lab ×13 | ❌ 空白 | 需 OCR |
| 微信照片（手机拍单据） | ×21 | N/A | 需 OCR + 图像预处理 |
| PNG 截图（医嘱） | ×4 | N/A | 需 OCR |

**结论**：真实场景中 **扫描件 + 照片占比 > 85%**。OCR 不是可选功能，是核心路径。文本型 PDF 直接抽取只是锦上添花。

### 1.6.2 关键发现与方案修正

#### 发现 J：双栏排版检验报告 —— 解析架构必须升级 ⚠️ 最高优先级

南京明基医院的检验报告单采用**左右双栏排版**，OCR 按行输出时两栏内容交错：

```
hsCRP
*超敏C反应蛋白
5.0
mg/L
0. 010. 0              ← 左栏参考范围 (0.0-10.0)
嗜酸性粒细胞百分比1.6    ← 右栏内容！被插入左栏中间
E0%
0. 4-8. 0              ← 右栏参考范围
...
△*白细胞 WBC 13. 71 10~9/L 3. 509.50
NEUT#中性粒细胞计数 10.22 10°9/L 1.806.30
RBC △*红细胞 3. 18 3.805.10
LYMPH#淋巴细胞计数 2.30 10°12/L ← 单位错位！淋巴应为 10^9/L
10°9/L
```

**风险**：顺序读取会把右栏指标错误地关联到左栏的数值和单位上。上面这个例子中，淋巴细胞的单位被错位成了 `10^12/L`（这是红细胞的单位），数值 2.30 配上 10¹²/L 是完全荒谬的。

**修正（解析架构升级）**：

原流程 `OCR → 纯文本 → 文本大模型抽取` 对双栏报告**不可靠**。改为三选一（建议组合使用）：

| 方案 | 说明 | 优先级 |
|------|------|-------|
| **A. 版面分析 + 分栏切分** | OCR 保留坐标 → 按 X 坐标中位数切分为左右栏 → 各自按 Y 排序 → 再抽取 | **推荐，成本低** |
| **B. 多模态大模型直接抽取** | VLM 看原图，理解版面后输出结构化 JSON | 准确率最高，成本较高 |
| **C. 表格检测算法** | 检测表格线，按单元格还原 | 对无线表格无效 |

**落地建议**：V1 用方案 A（坐标分栏）为主，对分栏失败的报告降级用方案 B（VLM）。**OCR 服务选型必须要求返回每个文本块的坐标（bbox）** —— 这与"原文回溯"需求一致，是同一个技术前提。

#### 发现 K：△ 和 * 是"互认标识"，不是异常标记 ⚠️

报告底部注明：

> 项目名称前注"△"为长三角互认；注"*"为省内互认项目。

而患者 A（海南）的报告用 ★ 前缀 + ↑↓ 箭头标记异常。**两家医院标记方式完全不同**。

| 医院 | 异常标记方式 |
|------|------------|
| 海南省肿瘤医院 | ★ 前缀 + ↑/↓ 箭头 |
| 南京明基医院 | **无显式异常标记**，△/* 仅为互认标识 |

**修正**：**不能依赖报告上的异常符号**。异常必须由系统统一计算：`结果 vs 参考范围`。

这带来连锁风险：**参考范围的解析准确率直接决定异常判定的准确率**。而参考范围恰恰是 OCR 错误重灾区（见发现 L）。

**缓解**：
1. 参考范围解析后做合理性校验（下界 < 上界、落在生理可能区间内）
2. 解析失败或存疑时，回退到指标字典的默认参考区间，并标注"使用默认参考范围"
3. 异常判定结果携带置信度，参考范围存疑时异常标记同步标为"存疑"（虚线显示，不实心标红）

#### 发现 L：参考范围解析是 OCR 错误重灾区

观察到的真实错误：

| OCR 输出 | 实际值 | 错误类型 |
|---------|--------|---------|
| `3. 509.50` | 3.50–9.50 | 连字符丢失 + 小数点后空格 |
| `1.806.30` | 1.80–6.30 | 同上 |
| `0. 010. 0` | 0.0–10.0 | 同上 |
| `35.045.0` | 35.0–45.0 | 同上 |
| `0.100.60` | 0.10–0.60 | 同上（歧义：也可能是 0.100 和 0.60） |
| `10~9/L` | 10⁹/L | 上标符号 ^ 识别为 ~ |
| `10°9/L` | 10⁹/L | 上标符号 ^ 识别为 ° |
| `×1012/L` | 10¹²/L | 上标完全丢失 |

**修正**：数字格式预修复层（见发现 B）增加两条专门规则：

1. **范围修复**：匹配 `数字 数字` 连续模式，结合列位置（参考范围列）判定为区间，插入连字符。歧义情形（`0.100.60`）用值域校验裁决：优先选择使"下界<上界且均落在生理区间"的切分
2. **上标单位修复**：`10~9`、`10°9`、`1012`、`10 9` → 归一化为 `10^9` / `10^12`，再与字典单位匹配

#### 发现 M：医院检验报告已自带"AI 解读" —— 差异化定位需要重新明确

南京明基医院检验报告单底部明确印有 **「AI解读（仅供参考）」** 字样。

**含义**：
1. 单张报告的 AI 解读，医院 LIS 已经在做，这不是我们的护城河
2. 但医院提供的是**单次、单院**的解读，**没有任何一家提供跨时间、跨医院的纵向趋势管理**

**修正**：产品定位进一步聚焦——

| ❌ 不是我们的价值 | ✅ 我们的独特价值 |
|------------------|------------------|
| 单张报告的指标解读（医院已有） | **跨时间的纵向对比与趋势** |
| 单次异常的医学含义（医院已有，且我们不合规） | **跨医院的数据归集与统一** |
| — | **跨院治疗的完整时间轴**（患者 B 就跨了江苏省人民医院和南京明基医院） |

患者 B 的样本中，出院记录引用了**江苏省人民医院** 2026-07-03 的外院 CT 结果（带 UUID 编号）。跨院就诊是常态，而没有任何一家医院的系统能看到患者在其他医院的完整数据。

#### 发现 N：病理报告的结构化字段完全可抽取

#### 发现 O：基因检测必须精确到密码子位点

两位患者的 KRAS 突变位点不同，临床意义也不同：

| 患者 | 基因检测结果 | 样本类型 | panel |

### 2.1 五层数据结构

### 2.2 核心实体关系

```
Patient（患者）
  ├── Diagnosis（诊断，系统推断 + 用户可覆盖）
  ├── Encounter（就诊/住院事件）—— 时间轴节点
  ├── TreatmentCycle（治疗周期）—— 时间轴锚点
  ├── Document（原始单据）
  │     ├── Exam（一次检查）
  │     │     ├── LabItem（检验指标项）  ← 绑定原文 bbox 坐标
  │     │     └── LesionMeasurement（病灶测量值）
  │     └── OCRText + 原文文件
  ├── GlucoseRecord（血糖记录，日内多点）  ← 独立子表，见 2.2.2
  └── IndicatorDict（指标字典，全局共享）
```

#### 2.2.1 血糖监测的独立子表（v1.2 新增）

**问题来源**：余曼华样本中，患者治疗期间新发糖尿病（HbA1c 8.8%），医嘱要求 7 点血糖谱监测（空腹 + 三餐后 2h + 睡前 + 凌晨）。这不是"一次检查一个值"，而是**一个患者在同一天内产生多个测量值**。

普通 `LabItem` 模型（一次检查 → 一组指标）无法自然表达这种结构，强行塞入会导致同一天出现 7 条重复记录。

**解法**：`GlucoseRecord` 独立子表

| 字段 | 说明 |
|------|------|
| id, patient_id | — |
| measured_at | **测量时刻（精确到分钟）**，而非仅日期 |
| time_slot | 时段枚举：`空腹` / `早餐后2h` / `午餐前` / `午餐后2h` / `晚餐前` / `晚餐后2h` / `睡前` / `凌晨3点` / `随机` |
| value, unit | 数值（mmol/L 标准，mg/dL 需换算） |
| source | 数据来源：`护理记录`/`血糖仪自测`/`检验单`/`患者自记录` |
| document_id | 可空，关联原始单据（自测时为空） |

**视图要求**：血糖不参与纵向多列对比（列 = 日期的模型不适用），而是独立的 **"日内多点 × 多天"热力表**：

```
        空腹  早餐后2h  午餐前  午餐后2h  晚餐前  晚餐后2h  睡前  凌晨
06-01   7.2    9.6      —      12.3      —      13.6      8.1   —
06-02   6.9   10.2      —      11.8      —      12.1      7.4   —
```

**V1 处理**：数据结构预留，UI 在 V2 实现。V1 若遇到血糖值，按普通 LabItem 入库（一天一条），不展开日内视图。

**三层结构（单据 → 检查 → 指标）** 是整个模型的骨架：

| 实体 | 关键字段 |
|------|---------|
| **Document** | id, patient_id, doc_type（检验/影像/病理/病程/其他）, doc_subtype（血常规/CT/出院小结…）, 检查日期(+置信度), 医院, 原始文件路径, OCR 文本, 页数, 上传者, 上传时间, 解析状态, encounter_id |
| **Exam** | id, document_id, 检查日期, 检查类别, **影像专有**：部位/方法/病灶位置/大小/结论/与上次对比描述, **病理专有**：组织学类型/分化/pTNM/IHC 项 |
| **LabItem** | id, exam_id, 指标编码(字典), 原始名称, **value_type（数值/定性/半定量）**, 数值, **枚举值 enum_value**, **等级 grade（1+/2+/3+/±）**, 单位, 参考区间上下限, **参考枚举值**, 异常级别, 置信度, **原文 bbox 坐标**（原文回溯的核心依赖） |

> **设计要点**：`LabItem.原文bbox` 必须在解析阶段就落库。这是"接受准确率、靠原文回溯兜底"这一策略的技术前提，事后补代价极大。

### 2.3 指标字典设计

**自建中文指标字典，不强制绑定 LOINC（预留 code 字段）。** 原因：国内项目命名与 LOINC 对齐比例不高，早期强绑定会拖慢迭代。

| 字段 | 说明 |
|------|------|
| code | 内部标准编码（如 `CBC.NEUT#`、`URINE.PRO`） |
| 标准名 / 别名表 | 每指标 5–10 个别名，V1 约 400 条别名 |
| **value_type** | `numeric` / `qualitative` / `semi_quantitative`（见发现 R） |
| **枚举值域** | 仅定性/半定量指标需要，如 `阴性 / 弱阳性(±) / 阳性(1+) / 阳性(2+) / 阳性(3+)` |
| 标准单位 + 换算规则 | 见下表（定性指标无单位） |
| 生理值域 [min, max] | 用于值域校验，超出即拒绝入库（仅数值型） |
| 默认参考区间（按性别/年龄） | 单据未印参考区间时的兜底。定性指标的默认参考为枚举值（如"阴性"） |
| 所属 panel | 血常规 / 肝功能 / 肾功能 / 电解质 / 肿瘤标志物 / **尿常规** / 凝血 … |
| 癌种权重 | 用于自动排序（只影响展示，不影响收录） |

> **v1.2 补充**：尿常规等定性/半定量指标的引入，使字典从"数值型专用"扩展为三类并存。这不只是加字段——**异常判定逻辑也要跟着分叉**（见 3.6 节）。

**单位换算规则（示例）**

| 指标 | 标准单位 | 常见异单位 | 换算 |
|------|---------|-----------|------|
| HGB | g/L | g/dL | ×10 |
| PLT | 10⁹/L | 10¹²/L | ×1000 |
| Cr | μmol/L | mg/dL | ×88.4 |
| Ca | mmol/L | mg/dL | ×0.25 |
| GLU | mmol/L | mg/dL | ×0.0555 |

### 指标分级策略（v1.2 修订）

扩大指标覆盖会稀释校验质量。解法是**分级而非平铺**：

| 级别 | 数量 | 校验强度 | 别名表 | 说明 |
|------|------|---------|--------|------|
| **Tier 1 核心** | 70 | 全四层校验（值域 + 内部一致性 + 历史对比 + 低置信度） | 完整（8–12 条/指标） | 肿瘤随访高频指标，直接影响治疗决策。**准确率目标 95%+** |
| **Tier 2 扩展** | 55 | 仅值域校验 + 历史对比 | 基础（3–5 条/指标） | 按需检查项目，解析入库并展示，但校验规则简化。**准确率目标 90%** |

> 分级原则：**投入与临床重要性成正比**。Tier 1 的每个指标都要写全内部一致性规则（如血常规的分类百分比加和校验），Tier 2 只做基本的量级拦截。新增癌种时，先把该癌种的特异指标从 Tier 2 提升到 Tier 1。

### 2.4 时间轴模型

**核心判断：肿瘤患者的时间是按治疗周期排的，不是按日历。**

时间轴的三级锚点：

```
治疗周期（C1、C2、C3…）
   └── 周期内日期（D1、D8、D15）
         └── 检查节点（血常规 / 生化 / 影像 / 疗效评估）
```

**为什么重要**：同样是"白细胞 3.2"，发生在化疗后第 10 天（预期谷值）和第 21 天（下一周期前）意义完全不同。脱离周期看指标，纵向对比会得出错误结论。

**治疗周期的自动推断（V2）**

| 步骤 | 方法 |
|------|------|
| 1 直接抽取 | 从出院小结/化疗记录中识别"第 X 周期""XX 方案" |
| 2 时序推断 | 抽不到时：检测血常规谷值的周期性（如每 21 天一次）+ 住院记录聚类 → 自动编号 |
| 3 零摩擦确认 | 非阻断提示："识别到 3/15、4/5、4/26 三次住院，看起来是每 3 周一个周期，【对】【不对】" |
| 4 兜底 | 用户不点也照常使用，标注为"系统推断" |

> **患者不需要知道"第几周期"**。这是系统内部锚点，界面上可不出现，只在生成纵向对比视图时用于分组。

## 3. 功能设计

### 3.1 单据归集与上传

**支持格式**（按实际优先级排序）

| 格式 | 实际占比 | 处理方式 |
|------|---------|---------|
| 图片（手机拍照/扫描件照片） | ~60% | 预处理 → OCR → 抽取 |
| PDF（扫描型） | ~25% | 转页为图 → 同上 |
| PDF（文本型/HIS 导出） | ~15% | 直接抽取文本层（跳过 OCR，准确率最高） |

**批量导入流程（V1 核心体验）**

```
相册批量选图（一次 20 张）
  ↓ [1] 轻量模型过滤非单据照片
  ↓ [2] 自动裁边 / 纠偏 / 去阴影 / 对比度增强
  ↓ [3] 自动分类单据类型（血常规/生化/CT/病理/出院小结…）
  ↓ [4] 自动抽取检查日期
  ↓ [5] 相似度去重（同一张重复拍摄）
  ↓ [6] 后台队列解析，前端显示进度
  ↓ [7] 结果确认页：按单据分组，低置信度字段标黄虚线
  ↓ [8] 一键入库
```

> **步骤 [3][4] 是批量导入的前提**。用户绝不会一张张标注"这是 3 月 5 日的血常规"。这两步做不了，批量导入就是伪需求。
>
> **历史单据是多数用户的第一次产品体验**——确诊半年后才开始整理的患者，手上往往已有 50–200 张单子混在相册里。导入体验不是次要功能，是转化率的第一道关。

**检索能力**：按时间范围、单据类型、医院、检查项目、关键词（OCR 全文）检索。

### 3.2 自动解析与四层校验

**解析流水线**

```
原始文件
  → 图像预处理（裁边/纠偏/去阴影/增强）
  → 文档分类（类型 + 子类型）
  → OCR（表格 OCR 优先，通用 OCR 兜底）★ 必须返回 bbox 坐标
  → 【版面分析】单/双栏检测 → 双栏按 X 坐标切分后各自按 Y 排序
       └─ 分栏失败 → 降级走「多模态大模型直接看图抽取」
  → 【第 0 层】数字格式预修复（范围连字符、上标单位、O/0 与 l/1 置换）
  → 【脱敏】替换姓名/证件号/住院号/医院名/医生名
  → 大模型结构化抽取（只传纯医学数据：项目名+数值+单位+参考区间）
  → 指标标准化（字典匹配优先，未命中走大模型映射并回写字典）
  → 异常判定（自算：结果 vs 参考范围）★ 不依赖报告上的异常符号
  → 四层校验
  → 入库 + 绑定原文 bbox 坐标 + 【回填】身份信息
```

> **v1.2 关键修正**：
> 1. **新增版面分析层**（对应发现 J）。双栏报告单若按行顺序读取会造成指标-数值-单位错位，必须在抽取前分栏。
> 2. **新增第 0 层数字格式预修复**（对应发现 B + L）。在值域校验之前执行，成本极低。
> 3. **异常改为自算**（对应发现 K）。不同医院的异常标记方式不统一（海南用 ★+箭头，南京用互认标识 △/* 而非异常标记），不能依赖报告符号。

**四层校验（C 端场景的关键设计）**

> **为什么必须自动校验**：C 端用户没有校对能力。把"淋巴细胞绝对值"的值抽到"中性粒细胞绝对值"上——数值完全合理，患者看不出来。用户校对这个安全阀在 C 端是失效的，所以拦错必须靠系统。

| 层 | 规则 | 拦截目标 | 处理 |
|----|------|---------|------|
| **1 值域校验** | 每指标内置生理可能范围（如 HGB 20–250 g/L） | 小数点错位、单位混淆、OCR 数字识别错误 | 拒绝入库，标为"存疑" |
| **2 内部一致性** | 见下方规则表 | **抽错行、指标错位**（最难发现也最危险） | 拒绝入库，标为"存疑" |
| **3 历史对比** | 与本人上次结果比对，差异 > 3 倍或跨越危险阈值 | 单位切换、重大录入错误 | 高亮提示 |
| **4 低置信度确认** | 前三层拦不住且模型置信度 < 0.9 | 疑难杂症 | 标灰 + 问号角标，点击进入对照模式 |

**内部一致性校验规则（血常规为核心）**

| 规则 | 容差 |
|------|------|
| 白细胞分类百分比之和 = 100 | ±3 |
| NEUT# ≈ WBC × NEUT% ÷ 100 | ±15% |
| LYMPH# ≈ WBC × LYMPH% ÷ 100 | ±15% |
| HGB ≈ RBC × 3（RBC:10¹²/L, HGB:g/L） | ±15% |
| HCT ≈ RBC × MCV ÷ 10 | ±10% |
| MCH ≈ HGB × 10 ÷ RBC | ±10% |
| MCHC ≈ HGB × 10 ÷ HCT | ±10% |
| TBIL = DBIL + IBIL | ±10% |
| TP = ALB + GLB | ±10% |

**准确率目标与取舍原则**

| 指标 | 目标 |
|------|------|
| 指标级 F1 | ≥ 95%（200 张真实单据测试集） |
| 严重错误率（量级错误 / 指标错位） | < 0.5% |
| 四层校验对量级错误的召回率 | ≥ 90% |
| **取舍原则** | **漏抽优于错抽**。没把握就不抽，标为"待补充"，后续可人工补录 |

### 3.3 原文回溯（一等公民设计）

既然策略是"接受准确率、靠原文回溯兜底"，这项功能必须做到极致。

**三个层级**

| 层级 | 交互 | 技术依赖 |
|------|------|---------|
| **单据级** | 时间轴上点任一检查 → 打开原始单据高清图 | 原始文件存储 |
| **指标级** | 点任一数值 → 跳转到原始单据对应页，**高亮框标出该数值在原文中的位置** | OCR bbox 坐标 |
| **对照模式** | 左右/上下分屏：左边结构化表格，右边原文。悬停左边任一行，右边自动滚动并高亮 | bbox + 前端联动 |

**置信度可视化**

| 置信度 | 视觉表现 |
|--------|---------|
| ≥ 0.95 | 正常显示 |
| 0.85 – 0.95 | 数值下方一条虚线 |
| < 0.85 | 数值标灰 + 问号角标，点击直接打开对照模式 |

**移动端适配**：点数值 → 弹出半屏原文浮层，自动定位并高亮，上滑可展开全屏。

**全局免责**：每个数据页面底部固定一行——"本页数据由系统自动识别，请以原始单据为准"。

> bbox 缺失时的降级方案：PDF 文本层可用文本匹配定位；扫描件 OCR 未返回坐标时，退化为"展示该页全文 + 关键词高亮"。

### 3.4 时间轴视图（双维度）

**核心设计：两种时间维度可一键切换，不互斥。**

| 维度 | 适用场景 | 展示方式 |
|------|---------|---------|
| **日历维度**（默认） | 找某天的单据、按日期回溯、给新医生看完整病史 | 纯时间倒序，节点 = 检查/就诊事件 |
| **治疗周期维度** | 判断化疗反应、对比同周期不同时间点指标变化 | 按方案分组 → 组内按周期排列 → 周期内按 D1/D8/D15 排列 |

**切换交互**

顶部一个 Tab 切换：「按时间」|「按治疗周期」，切换时数据不变、只改变分组和排序逻辑。

**日历维度（默认视图）**

- 纵轴：时间倒序（最新在上）
- 节点类型：就诊/住院、化验、影像、病理、治疗周期开始、手术
- 节点卡片：日期 + 类型图标 + 关键摘要（如"血常规 · 3 项异常"）+ 缩略图
- 顶部：类型筛选（全部 / 化验 / 影像 / 病理 / 治疗）+ 时间范围快捷选
- 底部：月份快速跳转（横向月份条）

**治疗周期维度**

- 一级分组：治疗方案（如 "NALIRIFOX"、"紫杉醇白蛋白+吉西他滨"）
- 二级节点：周期序号（C1、C2、C3…），标注起止日期
- 三级展开：周期内的检查事件（D1 化疗前血常规、D8 骨髓抑制谷值、D15 恢复期…）
- 同一周期内的事件天然对齐，方便看"这次化疗后 ANC 最低到了多少"

> **为什么两个维度都要**：日历维度解决"什么时候做了什么"（找单据），周期维度解决"每次治疗后身体怎么反应"（看趋势）。两者回答的是不同的问题。用户在两种场景间频繁切换——这也是真实使用中最常见的操作模式。

**V1 范围**：日历维度完整实现；治疗周期维度在 V2 引入（需要 L4 治疗数据解析完成后才有意义）。

### 3.5 纵向多列对比视图（核心功能）

**布局**

| 区域 | 内容 |
|------|------|
| 顶部工具栏 | Panel 过滤（血常规/肝功能/肾功能/电解质/肿瘤标志物）+ 时间范围（近 3 月/6 月/1 年/全部）+ 模式切换 |

| 单元格 | 数值 + 异常标记 |
| 行尾 | 迷你趋势线 sparkline（20×40px） |

**列数策略**（解决"一年 30 次血常规"的可读性问题）

| 模式 | 说明 |
|------|------|
| **关键节点模式**（默认） | 只显示关键检查点：每次化疗前、骨髓抑制谷值（ANC/PLT 最低点）、疗效评估节点、最新一次 |
| **完整模式** | 全部检查，横滑查看 |

**异常视觉分级**（避免满屏红色）

| 级别 | 判定 | 视觉 |

### 3.6 异常标记体系

**双基准设计**

| 基准 | 优先级 | 用途 |
|------|-------|------|
| **单据印刷的参考区间** | 主 | 判定是否超出正常范围。**优先用单据印刷值**，因为那是该实验室的标准；单据缺失时才用字典默认值 |
| **本人基线** | 辅 | 计算相对近 3 次均值的变化，仅作淡色提示 |

> **肿瘤特有判断**：对肿瘤患者，"相对本人基线的变化"往往比"是否在参考区间内"更有意义。晚期患者 CEA 长期 20（参考 < 5）可能是稳定的；另一患者 CEA 从 3 涨到 6（仍在"正常"范围）反而是危险信号。

**陈述性趋势标记（合规边界）**

| ✅ 可以做 | ❌ 不能做 |
|---------|---------|
| "近 3 次持续上升" | "建议尽快就医" |
| "较上次下降 35%" | "病情进展" |
| "低于参考区间下限" | "你出现骨髓抑制" |

**异常判定的两套逻辑（v1.2 新增，对应发现 R）**

由于指标分三类，异常判定不能只用数值比较：

| 类型 | 判定逻辑 | 分级方式 |
|------|---------|---------|
| **数值型** | `结果 < 下限` 或 `结果 > 上限` | 按超出比例分轻度/明显/显著三级 |
| **定性型** | `结果枚举 ≠ 参考枚举`（如"阳性" vs "阴性"） | 二分级：符合参考=正常，不符=异常 |
| **半定量型** | 先按等级枚举匹配（1+/2+/3+ 均为异常），数值仅作展示 | 按等级深度分级：±=轻度，1+=明显，2+/3+=显著 |

> **注意**：部分定性指标的"异常"无临床意义（如尿"颜色：淡黄色" vs 参考"黄色"），需在字典中标记 `abnormal_meaningful = false`，避免制造无谓的红色标记。

**参考范围不可信时的降级链**（对应发现 K + L + S）

```
单据印刷的参考范围（最优）
  → 解析失败/存疑 → 字典默认参考范围（按性别年龄）
  → 仍无 → 不做异常判定，仅展示数值，标注"无法判定"
```

任何一级降级都要在 UI 上标明来源，且异常标记相应降级为"存疑"（虚线，不实心标红）。

### 3.7 癌种自动推断

**核心原则：解析不分癌种，组织也不需要用户手动选择。**

```
用户什么都不选，直接上传
  → 系统从病理报告/出院小结自动识别诊断（如"右肺上叶浸润性腺癌 pT2aN1M0 ⅢA期"）
  → 自动加载对应推荐指标组（肺癌 → CEA、CYFRA21-1、NSE、ProGRP 置顶）
  → 用户可在设置中手动修正诊断，指标组立即重排
```

**防错设计（关键）**

> **指标组只影响"排序和置顶"，绝不影响"是否收录"。**

即使癌种识别错误，所有指标仍完整入库和展示，只是排序不理想。用户改一下诊断，1 秒重排，**零数据损失**。这比"注册时先选癌种"体验更好，也没有风险。

数据模型中"癌种"不是必填字段，仅在患者档案保留可选的诊断字段。

### 3.8 一页纸病情摘要（V2）

**生成逻辑**：数据已结构化，本质是已有数据的一种输出格式，边际成本极低。

**内容结构（A4 一页）**

```
[患者基本信息]  姓名/性别/年龄/联系方式
[诊断]          右肺上叶浸润性腺癌 pT2aN1M0 ⅢA期 · EGFR 19del(+)
[治疗时间轴]    2025-09 手术 → 2025-10~12 化疗 C1-C4 → 2026-01 起免疫维持
[核心指标趋势]  CEA / CYFRA21-1 近 8 次（表格 + 迷你趋势线）
[近期关键异常]  血常规 ANC 1.2（3/15）、ALT 78（3/15）
[最近影像结论]  2026-03-10 胸部 CT：右肺上叶病灶 2.1cm（前次 2.3cm），余同前
[基因检测]      EGFR 19del 阳性 / TMB 4.2 / PD-L1 TPS 15%
[页脚]          本摘要由系统自动整理，数据源于用户上传单据，请以原件为准
```

### 3.9 多患者与家庭协作（V3）

| 能力 | 说明 |
|------|------|
| 多患者 | 一个账号管理多位患者（如父母双方），切换式档案 |
| 成员邀请 | 邀请家人共同管理，可读写 |
| 权限分级 | 管理员（创建者）/ 协作者（读写）/ 只读（查看） |
| 操作日志 | 记录谁在什么时候上传/修改了什么，可追溯 |

> 肿瘤照护极少单人完成——子女轮流陪护、异地亲属想了解情况、不同人陪不同次门诊。不支持协作，实际使用中一定会遇到"那张化验单在你手机上吗"。

### 3.10 长辈模式（V4）

大字体、大按钮、只保留三个功能：拍照上传、看最近化验、看医生交代。隐藏所有复杂视图。

## 4. 合规与隐私

### 4.1 数据性质

肿瘤病案属于《个人信息保护法》定义的**敏感个人信息（医疗健康类）**，需单独同意。

### 4.2 数据处理原则

| 环节 | 措施 |
|------|------|
| 收集 | 单独同意书（非打包在用户协议里），明确告知用途、存储期限、撤回方式 |
| 存储 | 国内公有云对象存储，服务端加密（AES-256），传输全链路 HTTPS |
| **对外提供（调用大模型）** | **调用前自动脱敏**：替换姓名/证件号/住院号/医院名/医生名，只传项目名+数值+单位+参考区间等纯医学数据；解析后回填身份信息 |
| 访问控制 | 按患者档案隔离，协作者权限可撤销，分享链接可设有效期与随时收回 |
| 删除 | 支持患者档案级彻底删除（含对象存储文件），30 天冷静期后物理清除 |

> **脱敏不影响解析准确率**——抽取指标根本不需要知道患者是谁。这个设计必须在架构层一开始就埋进去，事后补代价很大。

### 4.3 功能红线

系统输出**只陈述事实，不做医学判断**。所有涉及异常的文案需经过合规话术清单审核，禁止出现诊断、建议、预后类表述。

## 7. V1 验收标准

| 维度 | 指标 | 目标值 |
|------|------|-------|
| **解析准确率** | 指标级 F1（真实单据测试集） | Tier1 ≥ 95% / Tier2 ≥ 90% |
| **严重错误率** | 量级错误 / 指标错位占比 | < 0.5% |
| **校验有效性** | 四层校验对量级错误的召回率 | ≥ 90% |
| **版面分栏成功率** ⚠️ | 双栏报告正确切分（无指标-数值错位） | ≥ 95%（分栏失败须能自动降级 VLM，不静默出错） |
| **参考范围解析准确率** ⚠️ | 参考区间上下界正确还原 | ≥ 95%（这是异常判定的前置依赖） |
| **异常判定准确率** | 系统自算异常 vs 人工标注 | ≥ 98% |
| **端到端时延** | 单张单据从上传到可查看 | ≤ 30 秒 |
| **批量导入** | 100 张单据处理完成 | ≤ 10 分钟 |
| **渲染性能** | 125 指标 × 20 次检查的对比视图 | ≤ 1 秒 |
| **原文回溯** | 点击数值到原文高亮定位成功 | 100%（PDF 文本层可降级为关键词高亮） |
| **脱敏有效性** | 送出请求中身份信息残留 | 0 |

> **⚠️ 标记项为 v1.2 新增**。这两项是样本校准后识别出的**前置依赖风险**——版面分栏失败会导致指标与数值错位（发现 J），参考范围解析失败会导致异常判定错误（发现 K+L）。建议在开发启动前先用现有 62 个样本文件做专项摸底测试，确认技术可行性再投入完整开发。

**测试集现状**：两位患者共 62 个文件（患者 A：20 PDF + 25 图片；患者 B：17 图片）。距 200 张的目标仍有缺口，建议按 10.3 节补充。

| # | 风险 | 等级 | 应对 |

### 10.3 遗留问题（进入设计阶段前补充）

1. **样本量仍需扩充**：两位患者**均为胰腺癌**。建议再收集 1–2 位**不同癌种**（如肺癌、乳腺癌、结直肠癌）患者的单据——不同癌种的标志物组合、治疗模式差异较大，直接影响 Tier1 指标的癌种权重配置
2. **双栏分栏算法需实测验证**：目前仅患者 B 的样本确认为双栏排版。需测试分栏算法在以下情形的鲁棒性：三栏报告、跨页表格、栏间有分隔线、无线表格。**建议开发前先用 20–30 张不同医院的化验单做分栏成功率摸底**
3. **OCR 服务选型实测**：需对比至少 2–3 家（腾讯云、百度、阿里）在真实样本上的表现，重点考察三项：① 是否返回 bbox 坐标 ② 参考范围的解析准确率（这是当前最大的错误源）③ 中文医学术语识别准确率。建议用现有 62 个文件建评测集
4. **Tier2 部分指标仍缺验证数据**：对患者 A 的 27 张图片做 OCR 后，**尿常规已获得真实样本**（并由此发现了定性/半定量指标的判定问题，见发现 R）。但**大便常规、心肌标志物、甲状腺功能、凝血功能**在两份样本中仍未出现，解析规则无真实数据支撑。建议对这些指标采取"宽松入库 + 标注待验证"策略
5. **CA19-9 的数值精度问题**：患者 A 2026-08-20 报告中 CA19-9 被识别为 `1327.661`（三位小数）。需确认是真实精度还是 OCR 错误（相邻报告均为两位小数）。建议值域校验增加"小数位数合理性"检查
