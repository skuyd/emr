# 本地 submit 使用指南

用户确认任务完成后，在 Codex 中手动调用个人技能 `$submit`；代理不得自行调用。该技能完成本任务
提交、本地验证、功能 PR Squash 合并、版本推断、Changelog、GitHub Release 及成功后的开发分支和 worktree 清理。版本计算仍由固定版本
Release Please 执行，依据合并标题和正文，不由模型猜版本。没有触发版本的变更会正常合并并报告“无需新版本”。

## 首次准备

- Windows 安装 Python 3.11、Node.js 22、Git，并准备 GitHub 凭据。
- WSL2 `Ubuntu-24.04` 中安装并启动 Docker Engine；默认 WSL 用户能执行 `docker info`。
- 在仓库运行 `npm ci` 安装锁定的 Release Please CLI。验证依赖由本地 Docker 构建缓存管理。
- 仓库 Actions 必须禁用；合并保护规则不能等待已停用的 Actions。详情见[版本规则](versioning.md)。

技能先读取当前仓库规则和 Git 状态，归纳当前任务的中文 Conventional Commit 标题。明确属于本任务
的未提交文件可以直接整理、提交；混入其他任务的变更或存在冲突时暂停相关动作并说明需要确认的范围。
不得使用 `git add -A` 把无法归属的文件一并提交。腾讯云本地资料始终排除。

## 执行与恢复

技能整理好提交后调用仓库工具，使用 UTF-8 正文文件避免 shell 转义改变内容：

```powershell
python tools/submit.py --title "feat(records): 新增报告导出功能" --body-file <正文文件>
```

从独立 worktree 提交时，调用 shell 的工作目录应位于主工作区，并用功能 worktree 中
`tools/submit.py` 的绝对路径执行，Python 解释器也须位于待删 worktree 之外。这样 Windows 调用进程
不会占用待删除的目录；正文文件也应放在 Git 公共目录或仓库外。

若工具建议全量并停止，先查看输出的测试目标和风险，再按当前候选给出的 digest 重新调用：
选择完整测试传 `--full-tests run --plan-digest <digest>`；选择相关测试继续传
`--full-tests skip --plan-digest <digest>`。候选变化后须使用新计划的 digest。

默认处理当前功能分支；显式 `--branch` 用于恢复原任务。工具的 `--dry-run` 针对工作区干净的
已提交候选，只检查和展示计划，不推送、不合并、不创建版本。尚有未提交改动时，技能只读展示
拟提交内容，不为预览先提交。详细参数以 `python tools/submit.py --help` 为准。

工具导出已提交候选的 Git archive，并保留该候选的 Git 身份与属性，供现有检查读取源码来源。
隔离快照不包含未跟踪文件、本地部署资料、宿主 Git 配置、凭据或其它提交历史。通过后创建或
更新功能 PR，以验证过的 head SHA 发起 Squash。发布候选由 Release Please 创建，本地通过后再
合并并创建标签及 Release。不调用 Jenkins、不部署、不强制覆盖远端提交、不重写标签。

状态、验证凭据和分组日志保存在 Git 公共目录的本地 submit 数据下，不提交到仓库。发生失败后
修复问题并以同一分支再次调用；工具核查远端事实再继续，不依靠上一次 HTTP 请求是否成功判断
是否已经合并。报告需要区分“功能已合并”“发布 PR 待验证”“Release 已创建”，不能统称成功。
若候选中的提交或验证工具与当前干净工作区版本不同，计划展示和验证会停止；可在包含候选工具版本的
干净工作区使用原分支、标题和正文恢复，不复制工具文件绕过检查。

## 成功后清理

功能 PR 已确认合并，且按需发布及 Release 状态核对全部成功后，工具最后删除本次的同名远端
开发分支、对应的独立 worktree 和本地开发分支。无需发版的变更在确认合并和无需发版后清理。
验证、合并或发布尚未完成时不执行清理；`--dry-run` 也不删除。

清理绑定本次已验证的提交和合并记录。本地或远端分支出现新提交、worktree 被更换、含未提交或
未跟踪文件，或存在可能隐藏改动的 `assume-unchanged` / `skip-worktree` 标记时停止清理。
远端删除使用指定旧 SHA 的 lease，避免删除并发推送的新提交。本地删除也
比较旧 SHA，适用于 Squash 后提交身份不同的情况。主工作区、其他任务的 worktree、发布分支及
Git 公共目录中的状态和验证证据均保留。若功能分支检出在主工作区，先保留并提示切换到其他分支，
再单独重试清理；工具不重置主工作区。

工具要求 origin 只有一个推送地址，并与查询使用的地址一致；配置了不同或多个 push URL 时停止，
避免验证一个远端却修改另一个远端。正常提交后的清理还绑定刚完成的 head，不能转而清理后来替换的任务记录。

独立 worktree 中只有依赖和缓存目录（`node_modules`、`.venv`、`__pycache__`、`.pytest_cache`、
`.mypy_cache`、`.ruff_cache`）可随目录清理。其他被忽略的本地文件也会阻止清理，避免丢失 `.env`、
运行数据、部署资料和本地证据。腾讯云资料须先按仓库规则保存至主工作区的
`docs/deployment/local/tencent-cloud/`，并核对完整性。

如果先前步骤成功、仅清理中断，结果明确报告“submit 已完成，清理待处理”。在保留的工作区中使用
包含本次工具版本的脚本重试；无需标题和正文，也不会重跑测试、合并或发布：

```powershell
python tools/submit.py --cleanup-only --branch <原开发分支名>
```

清理完成后重复此命令只返回原记录，不删除后来重新使用同名分支的新任务。

## 验证范围和耗时

`submit` 根据候选相对主线基线的实际差异生成验证计划，先输出各验证组及选择理由，再补齐缺少的
通过证据。PR 标题的 `docs`、`fix` 等类型不决定测试范围；commit、push、Squash、恢复执行这些
动作本身也不增加测试。无法说明某项变更影响哪些验证组时，停止并列出未识别的差异，不能静默全量。

| 实际影响 | 验证范围 |
| --- | --- |
| 已识别的普通文档、登记表、静态验证记录和 `prototype-gallery/screenshots/` 内的静态设计截图 | 文件及文档治理、需求追踪、发布门禁记录、版本一致性检查 |
| 原型页面、样式、行为脚本及其测试 | 原型自身相关测试，不运行业务全量 |
| 应用前端样式、模板和 JavaScript | 受影响页面的 UI、无障碍、JavaScript 和浏览器专项 |
| 单模块或多模块业务功能 | 各受影响模块及调用方的单元、集成、浏览器和数据库专项；多模块取并集 |
| 配置、依赖、迁移、权限和共享基础代码 | 相关专项与必要构建检查；影响无法可靠界定时建议全量，由用户选择 |
| 提交编排、验证引擎、执行器及其对应测试 | 提交流程专项及相关契约检查；这三个工具的源文件进入生产镜像，源码变化还需构建与 smoke |
| 发布候选中允许的版本字段及 Changelog 变化 | 发布契约、版本和文档检查，以及最终镜像构建与 smoke |

混合变更取受影响验证组的并集，不因同时有文档和代码就改为全量。文档组直接执行 Python 检查，
不准备 Docker、浏览器或数据库环境。计划先列出精确测试目标、命令、理由和未覆盖范围；没有可执行的
相关测试或无法归类的输入时停止。建议全量时先针对当前候选请用户选择：运行全量，或在相关测试通过后
继续并记录未覆盖风险。选择随候选或主线变化失效；未运行的全量不能记为通过。失败、跳过或空集合的
必跑专项不能充当通过证据，也不能自动扩大或缩小范围掩盖失败。

前端计划结合页面名、模板加载的资源和测试中的文件名引用，覆盖分段 `Path` 读取的样式与脚本；
首页同时选择 shell 浏览器测试。配置与依赖的 Linux 专项不选择 Windows 专属启动器测试，计划明确记录
该缺口；选择 Linux 全量也不能消除它。直接修改、删除或重命名 `deploy/start-local.ps1` 或
`tests/deploy/test_start_local_script.py` 时停止，待具备对应平台验证能力后处理。

文档范围包含普通 Markdown、文档登记表、已识别的静态验证记录及 `prototype-gallery/screenshots/` 内的静态设计截图。原型 HTML、
CSS、JavaScript 有自身测试；生产镜像输入、评估输入、
脚本、依赖、测试配置和未知文件不因位于 `docs/` 而免检；删除、重命名和文件模式变化也参与判断。
腾讯云本地资料始终不得进入提交。删除、重命名须同时检查旧路径和新路径；无法安全归类的变化停止说明。

完整验证保留原 CI 的 Python 回归、八个必跑浏览器文件、独立 PostgreSQL 并发、JavaScript、
Django 系统与迁移检查、文档/版本/追踪/发布门禁、合成质量评估和生产 Docker 构建 smoke。
原 CI 排除的离线 OCR 模型及外部环境门禁仍不代表已通过。浏览器、PostgreSQL 等必跑分组
跳过或空集合即失败；通用 Python 中的平台限定用例按原规则记录跳过。

速度优化来自以下可核验的复用，首次下载及构建通常更慢：

- 源码放在 WSL Linux 文件系统，复用依赖及 Docker 层缓存。契约和 Django 检查后，普通
  Python 与 PostgreSQL 回归使用独立源码、容器和数据库并行运行，最多两个重任务；其余
  分组及发布候选验证保持顺序执行。两组的原测试命令和通过标准不变。
- 每个验证组独立记录通过证据，绑定精确测试目标、相关源码、测试与依赖输入、验证策略、命令及实际环境
  指纹。只有这些内容匹配且日志、报告等证据摘要完整，才能复用；不同测试目标不能共用同一结果。
- Squash 只改变提交身份、源码树不变时复用已有验证。恢复提交时重新核验凭据和远端事实，
  不因恢复动作本身重复执行已通过的检查。
- 一组通过而另一组中断时，保存已通过组的证据。恢复时核验后仅补跑缺失或失效的组；例如
  PostgreSQL 已通过而 Python 中断，不重跑仍然有效的 PostgreSQL 组。失败、跳过或空集合不是通过证据。
- 业务验证后仅追加已识别文档时，业务组的相关输入未变就复用原证据，只补受影响的文档检查。
  新凭据保留复用来源和原覆盖范围，不冒充再次运行全量。更改执行器或验证策略后，相关组的旧证据不能沿用。
- 主线前进后先确定实际发布候选，不预先对中间主线做一轮全量。相对已验证基线只改允许的版本字段、
  在原 Changelog 前增加记录及已识别文档时，复用仍有效的验证组，补齐发布检查。专项计划也可作为
  发布基线，但 `business_reused=false`，不能记成复用了业务全量。额外的业务差异按实际影响重算计划；
  建议全量时由用户针对新候选重新选择，无法解释时停止，不能因缺少全量凭据而自动扩大到全量。
- 若发布候选的版本差异已确认安全，但没有可复用的业务凭据，且主线相对功能基线仅有文档变化，
  停止并说明缺少可证明的业务范围；文档检查不能冒充业务验证。
- 实际检查失败则停止，不自动切换模式、扩大验证或启动另一轮测试掩盖失败。修复后重新计算受影响组；
  指纹或产物失配的证据不可复用，缺失组必须补齐才能合并。
- 日志保存各组耗时及 pytest 慢用例；没有实测前不承诺固定提速比例。

Actions 禁用后不会新增日常 runner 用量，但历史 artifact/cache 的存储费用不会自动消失。
本流程不删除既有验证证据。GitHub Release 只代表源码发布，生产放行仍由
[发布门禁](../verification/release-gate.md)决定。

实施与实际验收状态见[实施计划](../plans/2026-09-26-local-submit.md)及文档登记表。
