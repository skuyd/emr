本修复落实[五批需求](../specs/2026-09-07-batches-one-five-requirements.md)中 B2-02 的即时撤权、
B2-04 的访问边界，以及 B5-01/B5-02 的日常记录与血糖表单权限。需求范围不变，不另立规格。

## 原问题与修复边界

成员打开日常记录或血糖编辑页后，提交无效表单。原实现只在成功 GET/HEAD 返回前复核
成员资格；400 错误页已经渲染数据库中保存的患者名时，即使另一请求已撤销成员，旧正文
仍可能返回。原独立反例确认患者名不来自提交内容，撤权也由真实成员服务完成。
同类风险包括无效筛选参数产生的 GET 400，以及协作者在渲染期间降为只读后的写入表单。

分支从实际主线 `3e43e59a2cffcdc6e165a62416273b1eae787293` 开始；应用修复提交 `12fde6d`
正常合流已合主线 `feca010` 后，冻结为 `ce7deb17b2efa4a34426a4b69553866255e081bc`。
相对该主线，应用与永久测试只改两处：

- `apps/core/decorators.py`：保留成功 GET/HEAD 的尾部复核，并对所有 HTTP 错误响应复核
  最初解析的患者、实际用户和最初所需权限；拒绝时关闭已构造的旧响应并传播权限错误。
- `tests/patients/test_error_response_access.py`：实际两域表单覆盖撤权、降为只读、账号失活和
  未变更控制，确认没有修订落库，已授权错误页仍保留输入。

已授权的 400 校验错误和 409 旧版本冲突保持原状态及内容。降为只读后仍合法的 GET 400
可返回，要求写权限的 POST 错误页则拒绝。成功写入的事务、跳转与编辑/删除/撤销行为不变。
此处只修患者权限门禁；原件、来源或记录自身在渲染期间变化的有效性检查属于各域门禁，
不能凭此修复宣称所有来源生命周期问题均已解决。
