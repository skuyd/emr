# “健康之家”暖笺全站 UI 与双重认证设计

日期：2026-08-31
状态：设计已确认，待实施计划

## 1. 背景与决策

项目已有一套可运行的 Django 用户端，以及四套静态 HTML 视觉原型。本次选择第一套“暖笺 · 家庭档案”作为全站设计方向，并允许在不改变核心业务能力与隐私边界的前提下调整导航结构、页面信息层级和用户文案。

已确认的关键决策：

- 产品名称统一改为“健康之家”，副标题为“家庭健康档案”。
- 用户端全部页面统一采用“暖笺”设计语言。
- 文案同时服务患者本人和家属，不默认用户只属于其中一种角色。
- 采用“设计系统驱动的全站重构”，不直接复制静态原型，也不只做表面换肤。
- 登录升级为手机号、密码和短信验证码的双重认证。
- 首次使用时先验证手机号，再设置密码；忘记密码时通过短信验证码重设。
- 开发环境预置手机号 `18000000000`、密码 `123321`、固定验证码 `230412`。

## 2. 目标与非目标

### 2.1 目标

1. 让首次进入的用户立即理解如何上传并保存健康资料。
2. 让用户能快速搜索、识别并打开目标原件。
3. 在所有页面明确区分原件与自动整理结果，维持用户信任。
4. 统一公开页面、登录后页面、状态反馈和危险操作的视觉与语气。
5. 在桌面和移动端都保持清晰、可访问且可操作的体验。
6. 用密码加短信验证码保护健康资料访问，同时保留首次使用和找回密码能力。

### 2.2 非目标

- 不改变文档存储、OCR、处理管线、实验指标提取或通知投递的业务规则。
- 不改变数据库中的健康资料结构或患者数据归属规则。
- 不增加诊断、治疗建议或疗效判断功能。
- 不重做 Django 管理后台。
- 不引入新的前端框架或外部字体服务。

## 3. 用户与设计原则

主要用户包括患者本人以及帮助家人整理资料的照护者。界面使用“自己和家人”“当前健康档案”等包容性表达，并通过患者名称持续标识当前操作对象。

设计原则：

- 原件优先：任何自动识别结果都不能比原始报告更具权威感。
- 温和明确：语气缓和压力，但不弱化风险、错误或危险操作。
- 一眼可用：上传、搜索和打开原件是最醒目的动作。
- 渐进增强：JavaScript 失效时，关键表单、导航和资料查看仍可工作。
- 可访问优先：颜色、焦点、语义、键盘和触控目标均纳入基础设计。

## 4. 全站框架与导航

### 4.1 公开页面框架

`base_public.html` 承载登录、首次使用、忘记密码、引导、隐私政策、敏感信息说明、账号删除完成和服务不可用页面。

公开框架包括：

- “健康之家”品牌标识与“家庭健康档案”副标题。
- 暖米色页面背景与居中内容卡片。
- 简洁页脚或辅助链接，不显示登录后的业务导航。
- 一致的表单错误摘要、隐私入口和返回路径。

### 4.2 登录后页面框架

`base_app.html` 承载全部登录后页面。桌面端取消现有左侧栏，采用暖笺原型的顶部导航。

桌面一级导航：

- 首页
- 健康档案
- 健康趋势
- 我的

顶部区域同时显示通知入口和当前档案标识，例如“林女士的健康档案”。上传入口不占用普通导航项，而是在首页和档案页使用赤陶色主按钮。

“任务”不再作为一级导航。上传处理进度放入首页状态区，完成或失败信息进入通知中心；现有 `/tasks/` 页面继续保留为完整状态列表，并可从状态区或通知进入。

移动端采用紧凑顶部栏与固定底部导航：

- 首页
- 档案
- 上传
- 趋势
- 我的

中间的上传入口视觉突出，并适配设备安全区域。

## 5. 页面信息架构与文案

### 5.1 首页

主标题为“把自己和家人的健康资料，安心收在一起”。页面首屏由说明文案与上传卡片组成，上传卡片强调：

- 支持图片和 PDF 批量选择。
- 无需补录医疗信息。
- 原件先保存，再自动整理。

首屏下方依次显示处理状态和最近资料。每份资料显示日期、名称、机构、状态与打开入口。

### 5.2 健康档案

页面标题为“收好的健康资料”。提供关键词搜索、类型筛选和日期浏览。资料以暖笺式时间线或卡片列表呈现，每项明确显示：

- 资料名称
- 报告日期
- 医疗机构
- 文件类型或页数
- 处理状态
- “打开原件”或“重新整理”动作

### 5.3 上传

页面标题为“把新资料放进健康之家”。流程为：

1. 选择文件。
2. 查看文件清单并确认上传。
3. 查看每个文件的保存和整理状态。

批量上传按文件显示结果，不能使用一个总提示掩盖部分成功或部分失败。上传完成后用户可以离开页面，任务在后台继续。

### 5.4 资料详情与原件查看

桌面端左侧展示原始报告，右侧展示自动整理结果；移动端始终先展示原件。页面保留：

- 原件翻页、缩放和大图查看。
- 自动整理字段及其来源页码。
- 点击字段定位原件来源。
- 下载原件。
- “识别不准确”反馈。
- 删除资料入口与独立确认页。

固定信任提示为：“自动整理结果可能不准确，请以原始报告为准。这里只帮助查找，不提供诊断或治疗建议。”

### 5.5 健康趋势

使用“看看指标随时间的变化”等中性表达。图表保持暖笺配色，但数据线、轴、标签和异常状态采用高对比设计。每个数据点可以返回来源原件。趋势页不能输出诊断、治疗或疗效结论。

### 5.6 我的

页面集中展示：

- 当前档案身份。
- 用户偏好。
- 通知设置。
- 隐私政策与敏感信息说明。
- 退出登录。

删除资料和注销账号放入独立的谨慎操作区域，并继续使用服务器渲染的确认页。

### 5.7 登录、首次使用与密码重置

公开认证页面使用“欢迎回到健康之家”“第一次使用健康之家”“重新设置密码”等直接文案。手机号、密码、验证码和错误信息都有持久标签，不以输入提示代替标签。

### 5.8 空状态与错误状态

示例文案：

- “这里还没有资料。”
- “没有找到相关资料，换个关键词试试。”
- “原件已经保存，自动整理可以稍后重试。”
- “部分文件未能上传，请查看下面的文件状态。”

错误文案必须说明当前结果、数据是否安全以及用户下一步可以做什么。

### 6.2 字体、空间与形状

- 中文大标题使用本地宋体风格字体栈。
- 正文、表单、数据与控制使用系统无衬线字体栈。
- 不从网络加载字体。

- 普通控件圆角为 12–16px，主要卡片和上传区为 20–24px。
- 医疗数据和原件工具区减少装饰，优先保证密度与可读性。

### 6.3 通用组件

建立并复用以下组件规则：

- 品牌标识
- 顶部导航和移动端底栏
- 当前档案标识
- 主按钮、次按钮、文字按钮和危险按钮
- 输入框、验证码输入、搜索和筛选
- 上传区与文件状态行
- 资料卡片与时间线条目
- 状态标签
- 通知面板与状态消息
- 空状态和错误摘要
- 确认页
- 原件查看器和来源定位

图标使用简洁线性 SVG，不使用表情符号承担功能含义。

## 7. 响应式与可访问性

- 重点验证 1440px、768px 和 390px 视口。
- 不允许整页横向滚动、内容遮挡或不可触达操作。
- 原件查看器、表格和趋势图在窄屏内部适配，不把溢出传播到页面。
- 正文和控件满足 WCAG AA 对比度。
- 键盘可完成所有主要操作，焦点轮廓清晰。
- 触控目标不小于 44px。
- 标题层级、地标、表单标签、错误关联和实时状态区域语义完整。
- 支持 `prefers-reduced-motion`，关键状态不依赖动画理解。
- “处理中、已整理、仅原件、处理失败”同时使用文字、图标和颜色。

## 8. 前端实现结构

- `static/css/tokens.css` 负责颜色、字体、间距、圆角、阴影、层级和状态变量。
- 公共组件样式与页面布局样式分离；页面 CSS 不重复定义全局令牌。
- `base_public.html` 与 `base_app.html` 提供两类统一页面框架。
- 导航、通知、当前档案标识、状态标签和资料卡片等重复结构拆成 Django 模板片段。
- 保持 Django 服务端渲染与现有原生 JavaScript，不引入 SPA 或新的组件框架。
- 保留现有 URL、表单字段契约、CSRF、权限、通知轮询、上传状态、原件查看和来源定位行为；认证流程需要新增的 URL 除外。
- JavaScript 只增强上传、轮询、通知和原件查看等交互。关键表单与导航具有无 JavaScript 后备流程。

## 9. 认证设计

### 9.1 登录

登录分为两个明确步骤。

第一步：手机号与密码。

1. 用户提交手机号和密码。
2. 服务端规范化手机号，通过手机号哈希查找账号并验证 Django 密码哈希。
3. 手机号不存在、账号不可用或密码错误时统一返回“手机号或密码不正确”。
4. 密码验证失败时不得创建或发送短信验证码。
5. 密码验证成功后，在服务器会话中写入短期 `pending_mfa` 状态，只保存账号 ID、安全的跳转目标和发起时间，不保存明文手机号或密码。
6. 服务端为该账号创建短信验证码挑战并发送验证码。

第二步：短信验证码。

1. 用户提交六位验证码。
2. 服务端要求有效且未过期的 `pending_mfa` 状态。
3. 验证码通过后消费挑战、清除 `pending_mfa`、轮换会话标识并创建正式登录会话。
4. 根据账号状态进入首次档案引导、原目标地址或首页。

验证码继续执行现有规则：五分钟有效、单次使用、最多五次输入尝试、手机号请求冷却、手机号小时/日限制和 IP 小时限制。

密码尝试增加按手机号哈希与 IP 的限流。失败响应保持一致，不泄露账号是否存在。所有登录、注册和重置步骤继续执行安全 `next` 跳转校验。

### 9.2 首次使用

1. 用户进入“首次使用”入口并提交手机号。
2. 服务端创建并发送短信验证码挑战。
3. 用户验证验证码后，服务器记录短期 `verified_phone` 状态。
4. 用户设置并确认密码。
5. 服务端创建新账号，或为该手机号对应的无可用密码账号设置密码。
6. 已有账号的资料与同意记录保持不变。
7. 完成后创建登录会话，并进入现有档案引导或首页。

账号只能在手机号验证码成功后创建，不能因为请求验证码而自动创建。

### 9.3 忘记密码

1. 用户提交手机号。
2. 页面始终显示不暴露账号存在性的通用结果。
3. 对存在且可用的账号发送短信验证码。
4. 验证成功后允许设置并确认新密码。
5. 新密码保存成功后撤销该账号全部已登记会话，用户返回登录页重新执行双重认证。

### 9.4 密码规则

- 使用 Django 的密码哈希接口保存密码，禁止明文或可逆存储。
- 正常注册和重置执行 Django 密码验证器，包括常见弱密码检查。
- 密码输入使用合适的 `autocomplete` 值，并提供显示/隐藏控制；控制必须可被键盘和辅助技术识别。
- 日志、分析事件和错误消息不得包含手机号、密码或验证码。

开发预置密码 `123321` 是仅限本地测试账号的例外，不降低生产注册和重置规则。

### 9.5 现有账号迁移

当前验证码登录创建的账号通常使用不可用密码。此类账号不能直接走密码登录；用户通过“首次使用”验证手机号后设置密码。该流程更新原账号，不新建重复账号，也不改变资料归属。

约束：

- 初始化脚本可重复运行，不能创建重复账号或破坏已有资料。

## 11. 状态、错误与安全边界

统一上传状态：

- 正在上传
- 已保存
- 自动整理中
- 已整理
- 仅原件
- 处理失败

表单错误显示在对应控件附近，并在页面顶部提供可聚焦的错误摘要。处理失败必须明确说明原件是否已经保存并提供重试入口。

认证安全边界：

- CSRF 保护覆盖所有状态变更请求。
- OTP、密码尝试和短信发送都有服务端限流。
- OTP 哈希保存、单次消费，禁止重放。
- 正式登录只在密码和 OTP 均通过后发生。
- 重设密码后撤销现有会话。
- 所有认证失败消息避免账号枚举。
- 现有手机号加密、哈希、隐私日志过滤和安全响应头继续保留。
- 删除资料和注销账号继续使用独立确认页，不能只依赖客户端弹窗。

## 12. 测试与验收

### 12.1 页面覆盖

覆盖登录、首次使用、忘记密码、引导、首页、上传、健康档案、资料详情、原件查看、健康趋势、任务状态、通知、我的、隐私说明、删除确认以及主要空状态和错误状态。

### 12.2 功能回归

保留并运行现有 Django、JavaScript、浏览器、安全和可访问性测试。浏览器流程覆盖：

- 首次使用和设置密码。
- 手机号与密码验证。
- 短信验证码第二步认证。
- 忘记密码与会话撤销。
- 上传、批量部分失败和处理状态。
- 搜索、筛选与打开原件。
- 来源定位、下载、反馈与删除。
- 趋势数据返回来源原件。
- 通知、个人设置与退出登录。

### 12.3 认证安全测试

至少覆盖：

- 正确密码加正确 OTP 登录成功。
- 错误密码不发送 OTP，也不创建登录会话。
- 缺少或过期的 `pending_mfa` 不能验证登录。
- OTP 错误、过期、锁定、消费后重放均失败。
- 不存在手机号与错误密码返回一致结果。
- 首次使用只在验证手机号后创建或升级账号。
- 现有无密码账号升级后资料归属不变。
- 密码重置后全部旧会话失效。
- 固定验证码无法在生产设置启用。
- 开发账号初始化幂等，且凭据不进入日志。

### 12.4 浏览器与视觉验收

- Chrome 和 Edge 作为正式验收浏览器，WebKit 作为兼容性参考。
- 在 1440px、768px 和 390px 视口验证布局。
- 为首页、档案列表、资料详情、上传、趋势、登录、首次使用和个人资料建立桌面与移动端视觉截图基线。
- 页面不得出现意外 JavaScript 控制台错误或意外 4xx/5xx 请求。

### 12.5 成功标准

1. 首次进入的用户能理解上传入口与原件保存机制。
2. 用户能快速搜索并打开目标资料。
3. 原件始终比自动整理结果更明确。
4. 全站品牌、导航、组件和语气统一为“健康之家”暖笺风格。
5. 用户必须同时通过密码和短信验证码才能访问健康资料。
6. 首次使用、账号升级和忘记密码流程可完成且不泄露账号状态。

## 13. 实施边界与风险控制

实施时应先建立令牌、公共框架和认证回归测试，再按页面迁移。每次迁移保留现有 Django 视图上下文、表单字段和 JavaScript 数据属性，除非实施计划明确给出兼容替换。

当前工作区已有与本设计无关的未提交修改。实现必须避开或保留这些修改，尤其不能覆盖 `static/css/viewer.css` 等已有工作。

主要风险包括：

- 导航重构导致现有任务入口变得不可发现。
- 静态原型结构直接迁移后遗漏生产状态和错误分支。
- 密码认证改造破坏现有 OTP 账号或浏览器测试夹具。
- 固定开发验证码误进入生产配置。
- 大范围 CSS 改动影响原件查看器和打印/嵌入布局。

相应控制措施是共享组件分层、页面逐批迁移、认证服务分离、生产设置检查、现有账号升级测试以及桌面/移动端浏览器回归。
