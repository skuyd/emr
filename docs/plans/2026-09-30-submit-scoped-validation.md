# submit 按影响选择验证范围实施计划

**目标：** 将 `$submit` 的业务验证从默认全量改为按实际影响选择，并保留可审计的全量选择和发布复用。

**设计：** [按影响选择验证范围](../specs/2026-09-30-submit-scoped-validation.md)。沿用现有计划、隔离候选和密封凭据机制；扩展计划中的精确测试目标与风险信息，不另建提交流程。

## 步骤与验证

1. **影响计划。** 先在 `tests/tools/test_submit_validation.py` 增加文档、原型、样式、配置、单/多模块、跨模块调用方、未知和混合变更的失败用例，再修改 `tools/submit_validation.py`。核对每个计划的路径、目标、组、理由和全量建议；无相关测试时停止。
2. **按目标执行与复用。** 先在 `tests/tools/test_local_validation.py` 复现现有 `planned` 仍调用全组命令、不同目标误复用、跳过或空目标等问题，再让 `tools/local_validation.py` 执行精确目标。确认命令、环境指纹、缓存键、JUnit/Node 结果和凭据包含相同目标；既有 `full` 命令范围保持。
3. **用户选择与发布。** 先在 `tests/tools/test_submit.py` 和验证引擎测试中复现建议全量时自动运行、拒绝全量后风险丢失、发布复用失败自动全量等问题，再修改 `tools/submit.py` 与 `tools/submit_validation.py`。确认选择仅对对应候选有效，相关测试失败时停止，发布阶段复用有效范围并始终构建及 smoke。
4. **入口与策略。** 更新个人 `$submit` 技能、`AGENTS.md`、`docs/policies/local-submit.md`、`docs/policies/versioning.md` 和必要的 README 描述；同步文档登记与索引。核对技能参数和工具 `--help`，运行发布自动化、版本及文档校验。
5. **集成复核。** 运行提交工具三个专项测试文件及按变更影响选取的额外检查；检查 Git 差异、暂存区和用户原工作区。记录实际通过、失败或未执行的项目，不调用 `$submit`、不创建 PR 或 Release。
6. **成功后清理（用户追加）。** 先复现命令成功后未清理的问题，再将本地和同名远端开发分支及对应独立 worktree 的清理加入最终步骤。临时 Git 仓库验证成功清理、前序失败保留、并发新提交和私有文件保护、主工作区保护及中断后单独恢复；更新工具指南和个人技能，运行提交流程专项与发布、版本、文档校验。
7. **提交前审查修复。** 用户明确调用 `$submit` 后，先复现独立审查发现的 Linux 配置计划误选 Windows 启动器测试、前端计划遗漏首页和上传页测试。使用仓库真实页面与测试建立修改、删除和重命名回归，明确平台缺口并保留必跑跳过失败门禁；独立复审后，由正式提交工具验证最终候选，再执行合并、按需发布和清理。
