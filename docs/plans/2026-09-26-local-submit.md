# 本地 submit 与验证复用实施计划

**目标：** 在 Codex 中一次调用完成本地验证、PR Squash 合并和 Release Please 发布，日常不运行 Actions；保持测试覆盖并消除重复执行。

**依据：** 用户已批准本会话完整方案并要求实施。使用个人 submit 技能、仓库 Python 工具、WSL2 Ubuntu 24.04、Docker 和固定版本 Release Please。保留现有版本规则、分支和 worktree；不部署、不调用 Jenkins，不改其他任务。

## 当前授权范围与成功标准

2026-09-28 用户最初确认先修纯文档和重复全量，随后明确要求按新的影响判断规则执行。
当前方案替代“所有非文档候选全量”及新增单独工具模式的做法：先生成验证组计划，再核验和补齐各组证据。
保留业务代码的现有完整门禁，不在本次按业务模块裁剪。依据是实际变更影响，不能从“使用 submit”推导出
必须运行 Python 业务全量或 PostgreSQL 回归。

- 普通文档只运行文档治理、追踪、发布门禁记录和版本四项检查，不准备 Docker 或数据库。
- 三个提交工具及其测试变化选择提交流程专项和相关契约；进入生产镜像的工具源码变化还需构建与 smoke。
- 计划在执行前列出验证组及原因；混合变更取影响并集，未知影响停止说明，不静默升级全量。
- 按组保存和复用通过证据，绑定相关输入、策略、命令、环境及产物摘要。一组中断不使另一组的有效结果失效。
- 发布可以沿用有效的专项计划基线，但 `business_reused=false`；只有额外业务差异才要求原业务完整门禁。
- 不把失败、中断、跳过或空集合记为通过；失败不自动换模式或重跑掩盖，失配证据不复用。

本轮实施和验证步骤：

1. 先用临时 Git 候选和模拟执行器复现误选全量及组间重复问题，覆盖混合、重命名、模式变化和未知影响边界。
2. 分离影响计划、组凭据和执行，验证 PostgreSQL 组通过而 Python 组中断时只补缺失组，并覆盖指纹和产物失配。
3. 将计划接入功能提交、恢复和发布，验证专项发布基线不会冒充完整业务回归，真实检查失败不会触发降级或额外全量。
4. 运行工具专项、文档/发布/版本契约和所选隔离集成及构建检查，独立审查后由本地 submit 交付；结果按实际证据填写。

## 实施与接口

1. 验证引擎：`tools/submit_validation.py` 根据真实 Git 差异生成受影响验证组及理由；通用 `planned` 执行计划选中的组，不增加仅供工具使用的特殊模式。导出精确候选的源码归档及仅含当前提交、树和文件对象的 Git pack，逐组核验输入、策略、命令、环境和证据后复用。发布差异仍须逐字段校验。验证结果包含候选身份、实际组结果和凭据路径；文档和专项凭据不能冒充完整业务回归凭据，失败抛出异常。
2. 本地环境：`tools/local_validation.py` 在 WSL 中接收候选归档、Git pack、源码身份、输出路径及验证计划，把源码解包至 Linux 文件系统，建立不含宿主配置或父提交历史的隔离 Git 快照并输出 `result.json`。文档组直接用 Python 检查，不准备或调用 Docker；按计划仅准备其他所选组需要的环境。原完整业务范围及命令保持，普通 Python 与 PostgreSQL 组都需要执行时仍隔离并行，最多两个重任务。逐组保存完成结果，中断恢复只补缺失或失效组；环境指纹不含 GitHub 凭据。
3. 提交编排：`tools/submit.py` 使用明确的分支、中文标题及正文文件执行；技能负责选择并提交本任务文件。编排器锁定 Git 公共目录，先输出功能/发布候选的验证计划及原因，核验证据后复核远端、合并、生成标签/Release并保存可恢复状态。先确定实际发布候选，不对中间主线额外执行全量；专项基线可用于发布，但如实保留其覆盖范围。
4. 迁移与入口：更新 Actions 为手动诊断、退役云端发布入口，同步发布校验与文档规范；创建个人技能。远端切换在本地验证通过后进行，并核查已有工作流、分支规则及 webhook。

同一业务分支在完整验证后仅追加文档时，业务组相关输入未变即可在核验证据及环境后复用，
只补文档检查；新凭据保留基线来源，不标记为重新执行了全量。
回归用例位于 `tests/tools/test_submit.py`、
`tests/tools/test_submit_validation.py` 和 `tests/tools/test_local_validation.py`；实际执行结果仍以
下述精确候选凭据为准。

## 验收

- 测试先行，覆盖字段级差异、缓存失效、失败/跳过不能复用、合并冲突、主线前进、网络超时后的远端事实核验及恢复。
- 使用临时 Git 仓库和模拟 GitHub API，不为测试制造正式版本。
- WSL 实际执行当前计划选中的验证组；记录分组耗时及 pytest 慢用例，复用结果时不重新运行重测试。
- 运行文档、发布自动化和版本一致性校验；独立审查后再执行远端迁移。

和交付报告中引用，不为追写 `verified` 状态而反复改变已验证的源码树。
